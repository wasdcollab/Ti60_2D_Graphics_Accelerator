# 最终技术架构与资源演进总览

> 本文档统合《未调用资源使用指南》、《最终阶段修复》（注：背景部分依主人要求已剔除）、《帧率优化底牌》与《帧率优化建议》四大文档的核心精髓，并经过底层硬件（Verilog/SpinalHDL）、Efinity 工具链机制与图形学原理的严格工程级审查。
> 
> **核心宗旨**：
> 1. **压榨闲置硬件资源**：将空闲的 128 个 DSP、13,993 个 SRL8 以及 105 块未用 BRAM 盘活，丰富 FPGA 硬件级加速开发，告别“纯搬运”架构。
> 2. **全弹幕双轨光效化**：采用 **方案 A（BitBlt 硬件饱和加法混合 `OP_ADD`）** 与 **方案 B（视频扫描端 SRL8 硬件 Bloom 滤镜）** 双轨驱动，既消除传统 Alpha 混合的毛玻璃变暗与 DDR 带宽击穿问题，又彻底规避 ColorKey 预烘焙光环在非纯黑背景下的“硬边黑框”穿帮。
> 3. **保留并规范原有的 `OP_ALPHA`**：现有硬件 Alpha 混合器保留不删，专职负责半透明黑色黑屏渐隐（Fade）、UI 半透明对话框、BOSS 暗色半透明气场护盾（Aura）等“遮挡/半透明/暗化”场景，各司其职。
> 4. **内容、特效与美术升级**：建立框架支撑后续快速增补符卡、粒子与美术元素（具体美术资产待主人下达指令）。
> 5. **打造独立压力测试关卡**：独立入口、免跑图、全光效全开、极限 192 颗弹幕风暴与高频招式，压测系统在极致负载下的 75 FPS 稳定性与硬件资源极限。
> 6. **原子化分步落地**：拆解为独立任务，每次仅执行一个任务，严格闭环验证。

## 二、四大关键技术路线

### 1. 固件“空间枷锁”破局方案

当前固件被 64,512 字节硬上限死死卡住（占用 64,432 字节，仅剩 80 字节余量）。

* **首选破局方案（零硬件风险，白嫖 12.3 KB 纯空间）**：
  - 审查 `sw/build/firmware.map` 发现：`sw/app/stage_bg.c` 中的三张关卡背景 RLE 压缩数据（`rle_stage_dream`、`rle_stage_lava`、`rle_stage_ice`）合计占用了 **12,313 字节（12.02 KB）** 片上 RAM！
  - 这三张背景开机只读一次用于解压到 DDR，常驻片上 RAM 是巨大的浪费。
  - **做法**：将这 12.3 KB 数据剥离至 DDR 资产区，开机直接从 DDR 读取解压。**固件瞬间净空 12.3 KB 纯代码空间**，足以编写 3,000 多行复杂弹幕逻辑与压测关卡，**0 Verilog 改动、0 IP 重新生成风险**。
* **备选方案【有争议 / 暂缓待定项】：片上 BRAM 硬件级扩容**：
  - **争议点审查**：直接修改 `settings.json` 不会触发 Efinity 自动重新生成 `soc.v`；且 96KB 并非 2 的整数次幂，易引发 SpinalHDL 内部地址译码对齐冲突；重新生成 Sapphire SoC 会重写 27,000 行代码，存在兼容性隐患。
  - **定论**：作为远期极端备选方案暂缓，优先采用背景剥离方案。

---

### 2. 全弹幕双轨光效与混合架构（方案 A + 方案 B + 保留 Alpha）

针对弹幕光效，彻底摒弃“ColorKey 预烘焙光晕”（因为其在非纯黑背景上会导致边缘出现实体深色“硬边黑框”）。采用 STG 行业正统的加法光效与 FPGA 特有的扫描端滤镜：

```
                    ┌────────────────────────────────────────────────────────┐
                    │                    STG 全局混合架构                    │
                    └───────────────────┬────────────────────────────────────┘
                                        │
        ┌───────────────────────────────┼───────────────────────────────┐
        │                               │                               │
┌───────▼───────────────┐   ┌───────────▼───────────────┐   ┌───────────▼───────────────┐
│ 【保留】OP_ALPHA 混合  │   │ 【方案 A】OP_ADD 饱和加法 │   │ 【方案 B】SRL8 扫描 Bloom │
├───────────────────────┤   ├───────────────────────────┤   ├───────────────────────────┤
│ • 位置：BitBlt 内部    │   │ • 位置：BitBlt 内部       │   │ • 位置：HDMI 视频输出端   │
│ • 公式：Src*a+Dst*(1-a│   │ • 公式：min(255, Dst+Src) │   │ • 原理：SRL8 3~5行高斯模糊 │
│ • 作用：暗化、遮挡、插│   │ • 作用：能量叠加、白心高光│   │ • 作用：全屏高光外发光扩展│
│ • 场景：全屏Fade黑屏、│   │ • 场景：BOSS大激光、大玉、│   │ • 场景：192颗海量普通小弹 │
│   UI对话框、BOSS气场护│   │   高阶符卡弹、爆炸火花    │   │ • 核心优势：0 DDR 带宽开销│
│   盾 (Aura)           │   │ • 优势：黑底天然透明，免  │   │   极限满载 75 FPS 绝对稳定│
│                       │   │   DSP乘法，真高光叠加     │   │                           │
└───────────────────────┘   └───────────────────────────┘   └───────────────────────────┘
```

* **方案 A（BitBlt 硬件饱和加法混合 `OP_ADD`）**：
  - 东方 Project 与所有经典 STG 的光效标准：$Out = \min(255, Dst + Src)$。
  - 纯黑（RGB=0）天然透明（$Dst + 0 = Dst$），无需 ColorKey；光晕边缘与背景自然叠亮；多颗子弹重叠自动汇聚成刺眼纯白光心。
  - 硬件只需 8 位饱和加法器，免去 Alpha 混合消耗的大量乘法器。用于关键大招、激光柱与高阶符卡。
* **方案 B（视频扫描端硬件 Bloom 滤镜，利用 13,993 个闲置 SRL8）**：
  - 在视频从 DDR 读出送入 HDMI 的瞬间，利用 SRL8 构筑几行像素延迟线，对全屏高亮像素实时做 2D 硬件高斯模糊扩散。
  - DDR 里小弹只用单向最高速的 `OP_COPY`（单行仅读源写目，极快），光晕全由 FPGA 扫描端在送显途中实时“染色”产生。
  - **DDR 额外开销为 0**，是 192 颗弹幕风暴下稳锁 75 FPS 的终极护城河。

### 3. DSP 算力引入与 CPU 解绑路线

* **DSP-0（消除历史误判，开启 CPU 硬件乘除法）**：
  - 代码审查证实：VexRiscv 内部**原本就例化了 `MulPlugin`（已占 4 个 DSP48）和 `MulDivIterativePlugin`（硬件除法器）**！
  - 之前使用 `libgcc` 软模拟仅仅是因为 `sw/build_firmware.py` 误判写死了 `-march=rv32i`。
  - 只要更新为 `-march=rv32im`，乘除法软件循环瞬间清空，数学密集型弹幕计算速度提升 40 倍，**无需重新综合 FPGA**。
* **DSP-1（视频流 $3 \times 3$ 硬件色彩矩阵与全屏滤镜）**：
  - 消耗 9 个闲置 DSP，串联在 `u_video_dma` 与 `u_dvi_encoder` 之间。
  - 在 85.7 MHz 像素时钟下时序极充裕。固件通过 1 个 APB 寄存器实现：**受击闪白、符卡发动全屏红化、擦弹灰度慢动作、中毒偏色**，**0 CPU 开销、0 DDR 带宽开销**。
* **DSP-2（BitBlt 坐标旋转与缩放硬件加速预研）**：
  - 利用 8~16 个 DSP 在 BitBlt 引擎中加入旋转/缩放坐标变换，支持东方 Project 标志性的旋转米弹、倾斜激光与大玉缩放。

### 4. 独立压力测试关卡（Stress Test Lab）架构

* **免跑图独立架构**：在主菜单增设一级入口（`PRESS TEST` / `BURST LAB`）。
* **直接交火**：进入即为满屏弹幕风暴，跳过剧情对话与杂兵波次。
* **多波次极限负载注入**：
  - 弹幕池顶格释放（`MM_EBULLET_COUNT` 192 颗敌弹连续全屏发射）；
  - 全屏激光柱与切线全开；
  - 方案 A 加法高光与方案 B 扫描 Bloom 全开；
  - 实时双屏硬件遥测：直观展示最低帧率（Min FPS）、平均帧率、GPU cycles 占用、DDR 搬运字节数。

## 四、执行纪律与协作规范

1. **单任务执行原则**：每次只让 AI 执行《分步实施任务卡》中的一个编号任务，不跨任务抢跑。
2. **零退化铁律**：每一个任务提交前，必须确保硬件编译 `build_hw.bat` 全 PASS，且当前已达标的帧率基准绝不发生回退。
   **「帧率基准」包含两条**：正常游戏 **75 FPS**，以及**对比模式（RENDER LAB）的 FPGA 侧 75** ——
   后者的验收口径、以及「不得借对比模式之名夹带改引擎参数」的红线，见
   《最终阶段修复.md》第一节「六」。
3. **资源红线监控**：
   - 固件镜像严格限制在片上 RAM 边界内（0xF9000000 ~ 0xF900FC00）；
   - 硬件时序必须满足 Timing Slack > 0（0 违规）；
   - 保持 CRLF / LF 换行符与文件编码规范。
