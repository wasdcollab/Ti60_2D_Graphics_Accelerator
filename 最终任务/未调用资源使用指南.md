## 一、为什么 DSP 几乎没被调用

### 1.1 实测答案：32 个 DSP 全部集中在两处

从 `outflow/ti60_top.res.csv` 的 DSP/MULTs 列（实测）：

| 层次 | DSP 数量 | 自身使用 |
|---|---|---|
| `ti60_top` | 32 | 0 |
| └ `u_sapphire_soc` | 4 | 0 |
| &nbsp;&nbsp;&nbsp;&nbsp;└ `system_cores_0_logic_cpu:VexRiscv` | 4 | **4** |
| └ `u_bitblt` | 28 | 0 |
| &nbsp;&nbsp;&nbsp;&nbsp;└ `u_alpha_blend:bitblt_alpha_blend` | 28 | **28** |

**结论（实测）**：整个设计里 87.5% 的 DSP 在 **alpha 混合单元**（28 个），
剩下 12.5% 在 **CPU 核 VexRiscv**（4 个）。
其余所有模块——DDR3 控制器、视频时序、地址生成、RLE 解压、DVI 编码——
**一个 DSP 都没用**。

### 1.2 根本原因：这条数据通路上没有「乘法形状」的运算

DSP 块只在综合器识别出「变量 × 变量」时才被调用。本项目从头到尾做的是
**搬运（copy）** 而不是 **计算（compute）**：

| 模块 | 在做什么 | 运算形状 | 需要 DSP？ |
|---|---|---|---|
| BitBlt 搬运通路 | 地址递增 + 数据直通 | 加法器 | ❌ |
| `bitblt_stride_gen` | 行地址累加（356 个 ADD） | 加法器 | ❌ |
| `bitblt_align_shifter` | 位对齐（74 个 ADD） | 移位 | ❌ |
| 视频时序生成 | 计数器比较 | 比较器 | ❌ |
| RLE 解压 | 查表 + 计数 | 查表 | ❌ |
| `dvi_encoder` | TMDS 编码（141 个 ADD） | XOR / 加法 | ❌ |
| **`bitblt_alpha_blend`** | **`src×α + dst×(1−α)`** | **乘法** | ✅ **28 个** |

所以 **DSP 利用率低不是设计缺陷，而是工作负载天然没有乘法**。
alpha 混合是全设计唯一的乘法运算，而它已经被 28 个 DSP 很好地实现了。

> **修正一条此前写下的推测**：曾怀疑 alpha 混合可能用移位近似（`>>8`）实现，
> 因此不消耗 DSP。**实测否定了这个推测**——它确实用了 28 个真正的硬件乘法器。
> 换句话说，alpha 混合这条路径已经是硬件最优的，没有优化空间。

### 1.3 ⚠️ 待核实：CPU 里那 4 个 DSP 与 `MULDIV_EXT=0` 矛盾

资源报告明确显示 `system_cores_0_logic_cpu:VexRiscv` 自身使用了 **4 个 DSP/MULT**。

但此前的结论是：软核配置为 RV32I，`MULDIV_EXT=0`、`BARREL_SHIFTER=0`，
因此 C 代码里的每个 `*` 都被编译成 `__mulsi3` 的移位-加法软件循环（约 41 条指令），
乘法完全不进硬件。

**这两件事无法同时成立**，必须核实。三种可能的解释：

1. `ip/soc/settings.json` 里的 `MULDIV_EXT` 实际不为 0（此前的记录有误或已被改动）；
2. `MULDIV_EXT=0` 只关掉了 DIV，MUL 仍在（即「有硬件乘法但不生成 `mul` 指令」）；
3. 那 4 个 DSP 被 VexRiscv 用于其它目的（非乘法）。

> **2026-09-22 补充（已实测）**：已读取 `ip/soc/settings.json`，确认
> `"MULDIV_EXT": "1'b0"` 与 `"BARREL_SHIFTER": "1'b0"` 的取值**都是 0**。
> 因此**解释 1 被排除**，这个谜团缩小到解释 2 或解释 3。
> 同时确认 `"OCRSize": "65536"`、`"ICacheSize": "4096"`、`"DCacheSize": "4096"`、
> `"DDRSize": "32'd3758096384"`（见 §3.4 路线 A 的前置条件）。

> **2026-09-25 补充（已实测，仍未结案）**：直接读已生成的 `ip/soc/soc.v` 网表，
> 里面**确实存在** `MulPlugin`（`writeBack_MulPlugin_result`、`execute_MulPlugin_a/b`、
> `memory_MUL_LOW` / `MUL_HH` / `MUL_HL`）与 `MulDivIterativePlugin`
> （`div_stage_0_outNumerator` / `div_counter_valueNext` 等），并且
> `outflow/ti60_top.hier_util.rpt` 显示 `VexRiscv` 自身占 **4 个 DSP**。
> 也就是说：**参数写 0，网表里却有乘法/除法硬件**。
>
> 结论更新：**上面「解释 1 被排除」这句话撤回** —— settings.json 的取值与
> 实际生成的硬件可以并存，最可能是 `MULDIV_EXT` 在该生成器里并不控制
> MulPlugin 的例化（或该参数被忽略 / 语义与名字不同）。
>
> **仍未结案的部分**：CPU 是否真的**译码** `mul` / `div` 指令 —— 这才是
> 《02_分步实施任务卡.md》任务卡 02 能否直接用 `-march=rv32im` 的唯一依据。
> **验证路径（必须实测，不接受推断）**：反汇编现有固件确认 `__mulsi3` 仍被调用
> （按 `-march=rv32i` 应当如此）→ 用 `-march=rv32im` 再编一版，确认链接里
> `muldi3.o` / `div.o` 消失 → **上板跑一遍**。风险是外显的：若硬件不译码 M 扩展，
> 非法指令会当场异常（"上板即崩"），不会变成"悄悄算错"。


**核实方法**（任选其一）：

- 读 `ip/soc/settings.json`，确认 `MULDIV_EXT` / `MulDivPlugin` 的当前取值；
- 反汇编固件（`sw/build_firmware.py` 产物），搜索是否存在 `mul` / `mulh` 指令；
- 在 `outflow/ti60_top.map.rpt` 里搜索 `VexRiscv` 附近的 MULT 原语实例名。

**为什么这条很重要**：如果 CPU 里已经躺着 4 个可用的硬件乘法器，
那么「启用硬件乘法」将是**零新增资源、零 PnR 风险**的性能提升，
收益是游戏逻辑中所有乘法快约 40 倍。这是全篇性价比最高的一条，应优先核实。

## 二、还有哪些资源没用

### 2.1 清闲排行榜

按「闲置比例」排序，见 §0 总览表。三个最值得注意的：

**① SRL8 —— 闲置 95.1%（13,993 个）**

SRL8 是用查找表实现的移位寄存器，用来做**延迟线、行缓冲、浅 FIFO**，
**不需要占用 BRAM**。这是本项目最被浪费的资源。

但要注意一个**实测**事实：当前 727 个 SRL8 里，**712 个（98%）是 DDR3 控制器
自己用的**：

| 层次 | SRL8 | 用途 |
|---|---|---|
| `u_ddr3_top` | 712 | — |
| └ `axi4_bus_ctl` → `rd_data_fifo_0` | **512** | 读数据 FIFO（C_DEPTH=32, C_WIDTH=129） |
| └ `local_bus_ctl` → `u1_lb_wrdata_fifo` | 144 | 写数据 FIFO（C_DEPTH=8） |
| 其余零碎（phy_ctl / ddr_phy_if） | 56 | — |
| **你自己写的逻辑合计** | **约 15** | bitblt / video_dma / i2c / dvi |

**即：官方 DDR3 IP 用 SRL8 实现了自己的浅 FIFO，而你自己的设计一个都没用。**
这说明 SRL8 完全可用来做 FIFO——只是你还没用上。

**② DSP —— 闲置 80%（128 个）**

闲置原因见 §1.2：不是没资源，是没活儿干。
要让它们忙起来，必须**主动创造乘法型功能**（见 §5）。

**③ XLR —— 闲置 52.8%（32,119 个）**

> 旧版此处写的是 22,556 / 37.1% / 闲置 38,244（62.9%），那是 2026-09-22 一轮的读数。
> 当前 `outflow/ti60_top.place.rpt` 的 Resource Summary 是 **XLRs: 28681 / 60800 (47.17%)**
> （其中 LUT4 10,832、LUT4+FF 5,451、Adder 1,882、SRL8 727、纯 FF 8,829）。
> 结论方向不变：逻辑资源仍然宽裕。

逻辑资源还有大把。加法器（ADDs）当前 **2,842** 个（旧版 2,809）；下面是 2026-09-22 版的
分层明细，总量小幅上涨、各项比例未变，用来定位"谁在吃加法器"仍然成立：

| 层次 | ADDs | 说明 |
|---|---|---|
| `u_bitblt` | 1,405 | — |
| └ `u_alpha_blend` | 796 | 与 28 个 DSP 配套的加法树 |
| └ `u_stride_gen` | 356 | 地址生成（本质就是加法） |
| `u_sapphire_soc` | 708 | 含 VexRiscv 347 |
| `u_video_dma` | 151 | — |
| `u_dvi_encoder` | 141 | TMDS 编码 |

### 2.2 BRAM 究竟被谁吃掉了（实测）

这是最关键的诊断。151 块 BRAM 的归属：

| 层次 | RAMs | 是否可控 |
|---|---|---|
| `u_ddr3_top` → `phy_ctl` | 22 | ❌ 官方 IP（cmd_fifo 5 + ctl_fifo 2 + dout_fifo 8 + din_fifo 7，深度仅 16） |
| `u_sapphire_soc` | 103 | ❌ 官方 IP + 固件 |
| └ `system_ramA_logic:BmbOnChipRam`（**OCR 固件 RAM**） | **64** | ⚠️ 见下 |
| └ `system_ddr_ddrLogic_cc_fifo` | 17 | ❌ 官方 IP |
| └ `io_input_cmd_queue` | 10 | ❌ 官方 IP（跨时钟域 FIFO） |
| └ `io_output_rsp_queue` | 7 | ❌ 官方 IP（跨时钟域 FIFO） |
| └ `VexRiscv`（含 I-Cache 6 + D-Cache 6） | 16 | ⚠️ 可通过 settings.json 调整 |
| └ 其它外设（uart / spi / 零碎） | 少量 | ❌ |
| `u_video_dma` → `async_fifo` | 12 | ⚠️ 跨时钟域，必须用 BRAM |
| `u_bitblt`（read_fifo 7 + dst_read_fifo 7） | 14 | ⚠️ 深度 256 / 192 |

> ⚠️ 报告中存在父子包含关系，**各项不能简单相加**，上表用于定位大户而非精确对账。

**关键结论（实测）**：

1. **OCR 固件 RAM 独占 64 块，是全设计最大的单项，占总 BRAM 的 42%。**
2. **你自己写的逻辑（bitblt 14 + video_dma 12）只占 26 块，其余 125 块全在官方 IP 手里。**
3. 所以「省 BRAM」的可操作空间**极小**：
   - 缩 OCR？固件当前 47,287 B / 64,512 B 可用（73.3%），
     缩到 48 KiB 只剩约 1 KB 余量，**后续还要加功能，不能缩**。
   - 改 I-Cache / D-Cache 大小？可以调，但各 6 块，收益有限且影响 CPU 性能。
4. **上表里那些 FIFO 不能简单「搬到 SRL8」**：
   - `async_fifo`、`io_*_queue`、`cc_fifo` 都是**跨时钟域** FIFO，
     而 SRL8 是单时钟域的移位寄存器，**无法替代双口异步 RAM**；
   - `bitblt_read_fifo` 深度 256 / 192，用 SRL 实现会消耗大量逻辑，不划算。

> **修正一条此前写下的建议**：曾提出「把 io queues 的 17 块 BRAM 迁到 SRL8」。
> 经实测确认，这些是跨时钟域 FIFO，**该建议不成立**，予以撤回。

## 三、BRAM 能否"解放"：SRL / DSP 迁移可行性分析

### 3.0 结论先行

> **不能。** 用 SRL 或 DSP 解放 BRAM 这条路走不通，原因很硬：
> **SRL8 的总容量只有 BRAM 的约 5.6%，而 DSP 根本不是存储器。**

| 设想 | 是否成立 | 原因 |
|---|---|---|
| 用 DSP 替代 BRAM 存储 | ❌ 不可能 | DSP 是硬核**乘法器**，不存储数据 |
| 用 SRL8 替代 BRAM 存储 | ⚠️ 理论可行，实际无意义 | 总容量仅 14.4 KiB，占 BRAM 的 **5.6%** |
| 迁移 BitBlt 的两个 FIFO | ❌ 不划算 | 要吃掉 **56% 的 SRL 总量**，只换回 14 块 BRAM |
| 跨时钟域 FIFO 迁移 | ❌ 不可能 | SRL8 是**单时钟域**的移位寄存器 |

### 3.1 DSP 为什么不能存数据

DSP 块的物理结构是硬核乘法器（乘法累加单元），它没有可寻址的存储阵列，
无法承担 RAM / FIFO / 缓存的任何一项功能。

DSP 与"省 BRAM"**唯一**相关的用法是**间接**的：**消灭对查找表的需求**
（用算法算出来，而不是查表查出来）—— 详见 §3.4 路线 B。

### 3.2 SRL8 的总容量只有 BRAM 的 5.6%（实测推导）

#### 3.2.1 先确定一个 SRL8 单位有多大

用 DDR3 IP 里的两组 FIFO 数据反推（数据来自 `outflow/ti60_top.res.csv`）：

| 层次 | 参数 | 报告中的 SRL8 | 反推 |
|---|---|---|---|
| `u1_lb_wrdata_fifo` | `C_DEPTH=8, C_WIDTH=144` | **144** | 8 深 × 144 宽 ÷ 8 = 144 ✓ |
| `rd_data_fifo_0` | `C_DEPTH=32, C_WIDTH=129` | **512** | 32 深 × 129 宽 ÷ 8 = 516 ≈ 512 ✓ |

两组数据同时吻合（后者是 4 个 8 深 SRL 级联 × 129 位宽），因此：

> **1 个 SRL8 = 8 bit 的存储容量**（8 位深 × 1 位宽）

#### 3.2.2 总量对比

| 资源 | 总量 | 等效存储容量 | 推算依据 |
|---|---|---|---|
| **SRL8** | 14,720 个 | 14,720 × 8 bit = **14.4 KiB** | 上述单位推导 |
| **BRAM** | 256 块 | 约 **256 KiB** | OCR 64 块 = 64 KiB → 每块 ≈ 8 Kb |

**结论：SRL8 的总容量只有 BRAM 的约 5.6%。**

即使把 14,720 个 SRL8 **一个不剩全部用光**，也只够替代约 **14 块 BRAM**
（占 BRAM 总量的 5.5%）—— 而且这还要求被替代的存储刚好是
"浅的、单时钟域的、不需要同时读写"的形状。

### 3.3 唯一能迁移的候选：BitBlt 的两个 FIFO（代价极端不划算）

#### 3.3.1 实测参数

`rtl/bitblt/bitblt_top.v`：

```verilog
parameter integer READ_FIFO_DEPTH = 192,
parameter integer DST_FIFO_DEPTH  = 192,
...
.DATA_WIDTH (128),
```

`rtl/bitblt/bitblt_read_fifo.v`：

```verilog
parameter DATA_WIDTH = 128,
parameter ADDR_WIDTH = 8,           // 2**ADDR_WIDTH storage entries
parameter DEPTH      = 256          // usable depth (<= 2**ADDR_WIDTH)
...
(* ramstyle = "block_ram" *) reg [DATA_WIDTH-1:0] mem [0:MEM_DEPTH-1];
```

> 注意最后那行 `(* ramstyle = "block_ram" *)` —— 这是**显式**指定用块 RAM。
> 也就是说，作者当初是**故意**选 BRAM 的，不是综合器自作主张。

#### 3.3.2 强行改成 SRL 的账

| 项目 | 计算 | 结果 |
|---|---|---|
| 单个 FIFO 容量 | 128 bit × 256 深 | 32,768 bit |
| 需要 SRL8 | 32,768 ÷ 8 | **4,096 个** |
| 两个 FIFO 合计 | 4,096 × 2 | **8,192 个** |
| 占 SRL 总量 | 8,192 ÷ 14,720 | **56%** |
| 换回 BRAM | — | **14 块 = 总量的 5.5%** |

> **投入 56% 的 SRL8，换回 5.5% 的 BRAM —— 血亏。**
>
> 而且 SRL 级联会显著拉长组合逻辑路径，给当前"0 违规"的时序结果带来风险，
> 属于用确定的收益换不确定的代价。

### 3.4 真正能省 BRAM 的三条路（都不靠 SRL / DSP）

#### 路线 A（唯一的大头）：把固件从 OCR 搬进 DDR 执行 —— 可省约 56 块（22%）

**这是唯一一笔"大钱"。**

- OCR = **64 块 BRAM = BRAM 总量的 42%**，是全设计最大单项
- 而它里面装的东西很简单：**47,287 B 的固件代码**（上一轮实测）
- 如果 CPU 改成从 DDR 取指（XIP，eXecute In Place），
  OCR 可以缩到 8 KiB（只留 bootloader + 栈 + bss）→ **省下约 56 块 BRAM**

**为什么现在具备条件**（实测确认）：

| 条件 | 实测值 | 结论 |
|---|---|---|
| DDR 地址段 | 低地址（`0x0080_0000` 起） | 与 OCR 的 `0xF900_0000` 不冲突 ✓ |
| SoC 的 DDR 译码窗口 | `DDRSize: 32'd3758096384`（3.5 GB） | 空间足够 ✓ |
| I-Cache | `ICacheSize: 4096`（4 KiB） | 需要它能挡住 DDR 延迟 ⚠️ |
| DDR 剩余空间 | 约 200 MB | 放 47 KB 固件绰绰有余 ✓ |

**风险与待验证**：

- 风险：中高。需要改 linker script + 启动流程 + `OCRSize` 配置，并重新全量验证
- **关键未知**：DDR 随机访问延迟（数百 ns 量级）vs 4 KiB I-Cache 的缺失率 ——
  代码本身局部性好，理论上可行，但**必须上板实测才能确认帧率不倒退**
- 若要保留部分 OCR 用于热代码/栈，缩到 16 KiB 仍可省 48 块（19%）

#### 路线 B（省未来的表）：用算的代替查的

DSP 不能存数据，但能**消灭对查找表的需求**——这才是 DSP 与 BRAM 的正确关系：

| 需求 | 现在的做法 | 改用算法 | BRAM 占用 |
|---|---|---|---|
| 旋转弹幕的 sin/cos | 查表 | **CORDIC**（只用加法器 + 移位） | **0 块** |
| 色彩变换矩阵 | 查表 | 硬编码 DSP 乘法 | **0 块** |
| 精灵缩放系数 | 查表 | DSP 乘法 | **0 块** |

> 这条路正好同时吃掉**清闲的 XLR + DSP**，是"用算术换存储"的正确姿势。
> 适用于**未来要新增**的功能，对现有 151 块 BRAM 没有直接回收效果。

#### 路线 C（小头，不推荐）：调 I-Cache / D-Cache

`ip/soc/settings.json`：`"ICacheSize": "4096"`、`"DCacheSize": "4096"`，各占约 6 块。

- 缩到 2048：各省约 3 块，合计 **6 块（2.3%）**
- 收益太小，且直接拖慢 CPU，**不推荐**

### 3.5 本节结论

> **SRL 太小（5.6%）、DSP 不存储 —— 两者都救不了 BRAM。**
>
> BRAM 唯一的出路是把那 **47 KB 固件从 64 块 OCR 里搬进 DDR**。
> 除此之外，BRAM 就是一块动不了的硬约束 —— 所以压榨时应**优先选择
> 不增加 BRAM 的功能**（算术型：DSP / XLR / SRL8），这与 §5 的路线一致。

## 四、片外资源：DDR3 里存了什么

### 4.1 物理容量：256 MB（实测 + 文档双确认）

- **颗粒型号**：`MT41J128M16JT-125`，2 Gb，16 位位宽（项目文档 `temp/基础部分技术路线.md` 确认）
- **从 DDR 控制器参数交叉验证**：
  `ROW_WIDTH=14 × COL_WIDTH=10 × BANK_WIDTH=3 × DQ_WIDTH=16 × RANKS=1`
  = 16,384 × 1,024 × 8 × 2 B = 268,435,456 B = **256 MiB** ✓

两条独立来源吻合，容量确认为 **256 MB**。

### 4.2 实测地址映射（来源：`sw/driver/memory_map.h`）

#### 帧缓冲

| 区域 | 地址 | 大小 |
|---|---|---|
| FRONT | `0x0080_0000` | 1366×768×2 B ≈ 2 MB |
| BACK | `0x00E0_0000` | ≈ 2 MB |

> `FB_LEFT_FRONT` 与 `FB_RIGHT_FRONT` 是**同一个地址**（`0x0080_0000`），
> BACK 同理。左右半屏不是两块独立缓冲，而是靠 VDMA 的半屏偏移
> （`HALF_OFFSET`）在**同一块缓冲内**分割。

### 4.3 用量总结（实测）

| 指标 | 数值 |
|---|---|
| 物理容量 | 256 MB |
| 已占用 | **约 56 MB** |
| **空间占用率** | **约 22%** |
| **剩余空间** | **约 200 MB** |
| 带宽占用率 | 约 24.6%（见 §2.2 相关分析） |

> **DDR3 是双重富矿：空间只用掉 22%，带宽只用掉 24.6%。**

### 4.4 由此得到的两条行动项

1. **把固件搬进 DDR 有充足空间**（47 KB vs 200 MB 剩余）
   → 这正是 §3.4 路线 A 成立的基础
2. **新增美术 / 素材可以放心往 DDR 里放**，空间不是约束；
   真正需要盯的是**带宽**（当前 24.6%，仍有约 3 倍余量）

### 4.5 顺带：DDR 布局的历史教训

`memory_map.h` 的注释里记着一段真实事故，值得保留：

> `MM_REIMU_TILT_L/R`、`MM_BURST_FRAME` 和 `MM_LASER_BAR` 曾经**全部落在
> `MM_STRIP_LAYER` 的范围内**，而视差层在第一次进入关卡时会被重建，于是：
> **船在推杆移动时消失、每次爆炸、每个 BOSS 激光柱都在读视差层的像素。**

现在已有 `tools/check_ddr_layout.py` 从 `memory_map.h` 重新推导每一个区间，
一旦发现两两重叠就让构建失败 —— 这类 bug 已被机制性防住。

**DDR 里没有的东西**：

- 固件代码（在 OCR 的 64 块 BRAM 里）
- 栈（OCR 顶部的 1 KiB，`__stack_floor = 0xF900FC00`）

## 五、压榨方案

### ⚠️ 先纠正一个方向

直觉上「压榨 FPGA」= 多用 DSP 跑得更快。但看完 §2.2：

> **DSP 闲 80% 只是没活儿干，不是性能损失；
> BRAM 的 59% 才是唯一的硬约束。**

所以压榨的正确姿势是：

> **只做「不增加 BRAM」的功能——也就是算术型的（DSP / XLR / SRL8）。
> 避开「需要缓存」的功能（行缓冲、属性表、更多帧缓冲）。**

---

### 🥇 P0 梯队：零资源成本，先做

#### P0-1. 修掉双 vsync 消耗（白送 60 FPS）

帧循环每帧消耗两个 vsync 脉冲（`main.c:4512` 的 `gpu2d_wait_vsync()`
加上后续四处 `while (GPU2D_REG_RIGHT_ACTIVE == right_back)`），
60 ÷ 2 = 30 FPS。

- **占用资源**：无
- **收益**：30 → 60 FPS
- **风险**：低（一行实验即可验证）
- **前置**：确认四处 `RIGHT_ACTIVE` 等待每帧实际触发几次

> 在动任何 FPGA 资源之前先做这个，性价比是无穷大（分母为零）。

#### P0-2. 压缩消隐提帧率（白送 77 Hz）

不改像素时钟，仅缩消隐：

```
H = 1366 + 16 + 32 + 16 = 1430
V =  768 +  1 +  3 +  1 =  773
```

- **占用资源**：无
- **收益**：59.94 → **77.44 Hz**
- **风险**：中（需确认显示器接受 77.4 Hz）
- **备注**：若改走「提高像素时钟到 107.25 MHz」的路线，需 TMDS fast clock
  达 1073 MHz，风险高，**不推荐**

#### P0-3. 核实并启用硬件乘法（待核实，潜在收益最大）

见 §1.3。若那 4 个 DSP 确实是可用的硬件乘法器：

- **占用资源**：**0 新增**（乘法器已经在，只是没被使用）
- **收益**：所有 `*` 从约 41 条指令的软件循环变成 1 条指令，**约 40 倍**
- **风险**：低（配置项改动）
- **前置**：核实 `settings.json` 的 `MULDIV_EXT` 与固件反汇编

---

### 🥈 P1 梯队：小资源、直接看得见的观感收益

#### P1-1. 精灵缩放（吃 DSP）

当前所有 sprite 都是轴对齐的 1× COPY，弹幕清一色「方方正正飞行」。
缩放需要 `x' = x · s`，就是纯 DSP 乘法。

- **占用资源**：DSP 约 4~8 个 + XLR
- **收益**：Touhou 弹幕的视觉张力直接上来（大玉、小玉、爆散）
- **风险**：中（要改 BitBlt 的地址生成通路，`bitblt_stride_gen` 需要插一级乘法）

#### P1-2. 精灵旋转（吃 DSP，收益最高）

```
x' = x·cosθ − y·sinθ
y' = x·sinθ + y·cosθ
```

- **占用资源**：DSP 约 8~16 个 + XLR（另需一张 sin/cos 查找表）
- **收益**：**旋转米弹是 Touhou 弹幕的灵魂**，视觉辨识度提升最大
- **风险**：中高（要处理边界/裁剪；查找表可放 BRAM 也可放 LUT ROM）
- **备注**：若 BRAM 紧张，sin/cos 表用 8 位精度 + 对称性压缩，或放 XLR 的 LUT

#### P1-3. 加法混合 / 精确 alpha（吃 DSP 或复用现有 alpha 单元）

在现有 `bitblt_alpha_blend`（28 个 DSP）基础上扩展混合模式：

```
ALPHA : dst = (src·α + dst·(1−α)) >> 8
ADD   : dst = min(255, dst + src)      ← 加法混合
```

- **占用资源**：**可复用现有 28 个 DSP**，或少量新增
- **收益**：弹幕发光、激光辉光、爆炸闪白——Touhou 视觉气质的一半靠这个
- **风险**：低（在已有混合单元上加模式选择）
- **前置**：确认现有 alpha 单元是否已有多模式寄存器位

#### P1-4. 全屏色彩矩阵（吃 DSP，实现成本极低）

RGB 3×3 矩阵 = 9 个乘法，DSP 的经典用法。

- **占用资源**：DSP 9 个 + XLR
- **收益**：一个 APB 寄存器即可控制全屏色调 ——
  **符卡背景变红、慢动作褪色、死亡灰化、受击闪白**
- **风险**：低（在视频输出通路上插一级矩阵，逐像素流水）
- **备注**：这是「观感收益 ÷ 实现成本」最高的一个

---

### 🥉 P2 梯队：吃 SRL8，为高级后处理铺路

#### P2-1. 行缓冲延迟线（吃 SRL8）

要做**外发光 / Bloom / 模糊 / 拖影 / 扫描线**这类效果，
需要「看到上一行（或上一帧）像素」的延迟线。

- **占用资源**：**SRL8**（这正是它的主场，闲置 13,993 个）
- **收益**：Touhou 的「弹幕发光」「幽灵拖影」效果
- **风险**：中（要改动视频通路的流水结构）
- **备注**：一行 1366 像素的延迟线用小 FIFO 拼，**不占 BRAM**——
  这是在 BRAM 紧张前提下唯一能做后处理的路径

#### P2-2. 自己写的浅同步 FIFO 改用 SRL8（吃 SRL8）

参考 DDR3 IP 的做法（它用 144 个 SRL8 实现了 `C_DEPTH=8` 的写数据 FIFO）。
未来新增的任何**浅的、单时钟域的** FIFO，都应优先用 SRL8 而非 BRAM。

- **占用资源**：SRL8
- **收益**：避免继续啃 BRAM 那 105 块的余量
- **风险**：低

---

### 🔧 P3 梯队：大改动，为架构升级铺路

| 编号 | 方案 | 占用资源 | 收益 | 风险 |
|---|---|---|---|---|
| P3-1 | **第二 BitBlt 通道** | XLR 数千 + BRAM 可能微涨 ⚠️ | 背景层/精灵层并行搬运 | 中高，需盯 BRAM |
| P3-2 | **硬件 OAM（精灵属性表）** | XLR + BRAM（属性表本身）⚠️ | CPU 只写属性，硬件自动渲染 | 高，架构级改动 |
| P3-3 | **硬件碰撞检测** | XLR | 弹幕 × 玩家判定下移到硬件 | 高，收益有限 |
| P3-4 | **硬件弹幕散布器** | XLR + DSP（角度累加/三角函数） | CPU 从弹幕生成中解放 | 中，需先确认 CPU 是瓶颈 |

> **P3-1 注意**：当前 BitBlt 引擎利用率仅约 0.7%、DDR 带宽仅约 24.6%，
> 并行度确实有余。但双通道**可能增加 BRAM**，而 BRAM 是唯一紧的资源。
> 做之前必须先评估 BRAM 增量。

## 六、结论（一句话）

> **不是 DSP 闲着可惜，是 BRAM 快满了该省着用。**
>
> - DSP 闲是因为**工作负载天然没有乘法**（唯一的乘法 = alpha 混合，已用满 28 个）
> - SRL8 闲 95% 是因为**官方 IP 之外的逻辑还没用上它**
> - BRAM 的 151 块里，**能自己调配的不到 30 块**，其余全在官方 IP + OCR 固件手里
>
> **推荐顺序**：
> ① 修双 vsync（免费 60 FPS）
> → ② 压消隐（免费 77 Hz）
> → ③ 核实并启用硬件乘法（潜在零成本 40 倍 CPU 提速）
> → ④ 色彩矩阵 + 加法混合（低成本、高观感）
> → ⑤ 缩放/旋转（真正吃掉 DSP 的视觉升级）
> → ⑥ 行缓冲后处理（用 SRL8 换高级特效）
