## 一、帧率优化：双屏对比跑满 + 正常游戏顶满 75 FPS

> **本节状态（2026-09-25 复核）**：下文「现象：30 FPS」是 2026-09-22 勘探时的读数，
> 修复已落地（新消隐 75.28 Hz、游戏帧循环一帧一个 vsync）。**唯一还没被钉死的是
> 对比模式（RENDER LAB）的 FPGA 侧读数** —— 见本节新增的「六」。

> **为什么排在第一位**：它是后面三项共同的地基。中期加的特效、后期补的画面，
> 都必须跑在这个基准之上；基准不立起来，后面所有「有没有变慢」都无从判断。

**现象**：上板实测（HUD 的 FPS 读数）游戏帧率只有 **30 FPS**。

**目标**：两个场景，**要求不一样**：

| 场景 | 垂直同步 | 目标 |
|---|---|---|
| **双屏幕 CPU vs FPGA 对比画面** | **关掉** | **不限速——帧率能跑多高跑多高** |
| **正常游戏**（弹幕 + 特效 + HUD 全开） | **要有** | **顶满 75 FPS** |

双屏那一场是**两种渲染方式的上限对比**：左边 CPU 软件画、右边 FPGA 硬件画，
把垂直同步摘掉就是为了看到两者真实的天花板分别是多少。这一场的读数**不设合格线**，
要的是**照实记录**（CPU 多少、FPGA 多少、差多少）。

正常游戏那一场反过来：**垂直同步必须开着**（否则画面撕裂），
帧率**顶满 75 FPS** 就是验收线。

**已完成的勘探结论（2026-09-22，未改动任何代码）**：

1. **30 FPS 的直接原因：帧循环一帧吃掉了两个 vsync 脉冲。**
   - `sw/app/main.c:4512` 的 `gpu2d_wait_vsync()`
   - 加上四处 `while (GPU2D_REG_RIGHT_ACTIVE == right_back)`（4602 / 4639 / 4648 / 4702）
   - `vsync_flag = frame_clear_axi` 来自 `video_dma_read.v:163` 的 `frame_clear_p`，
     一帧只在帧首出现一次；`active_base`（`video_dma_read.v:184`）也只在那时更新
   - 软件 publish 后 `right_back` 立刻翻转，而 `active_base` 要等下一帧才追上
     → 每帧必等第二个脉冲 → 60 ÷ 2 = **30 FPS**
2. **DDR 与 BitBlt 都不是瓶颈**：DDR 带宽占用约 24.6%，BitBlt 占用约 0.7%
3. **达到 75 FPS 不需要提高像素时钟**，压缩消隐即可：
   - `H = 1366 + 16 + 32 + 16 = 1430`，`V = 768 + 1 + 3 + 1 = 773` → **77.44 Hz**
   - 当前时序 1792 × 798 = 59.94 Hz

**待确认的算术（只对「正常游戏 75 FPS」这一场有效；双屏那一场不限速，不受它约束）**：

「压缩消隐即得 77.44 Hz」用的是**当前那颗像素时钟**（反推约 85.7 MHz，
即 `1792 × 798 × 59.94`）。把新消隐套到同一个时钟上：

| 像素时钟 | 新消隐后的刷新率 |
|---|---|
| 85.5 MHz | 77.35 Hz |
| 85.7 MHz（当前） | 77.53 Hz |
| 86.0 MHz | 77.80 Hz |
| **82.90 MHz** | **75.00 Hz** |

两个要留意的地方：

- **77.4 已经超出「75 ± 1」**。若验收口径真的是 75±1，就得同时把像素时钟降到
  约 **82.9 MHz**；如果口径改成「单 vsync 一帧、读数约 77」，那保持现时钟即可。
  **先定口径，再改消隐和时钟。**
- **帧率是 vsync 周期的整数分之一**，只有「每帧一个脉冲」和「两个脉冲」两种档位：
  77.4 Hz 下是 **77.4 FPS** 或 **38.7 FPS**，中间没有过渡值。
  所以「掉帧」会表现为直接腰斩，验收时要盯的是**有没有腰斩**。

### 已完成（2026-09-22）

**现象**：上板实测（HUD 的 FPS 读数）游戏帧率只有 **30 FPS**。

**目标**：双屏对比关掉垂直同步、不限速（如实记录）；正常游戏开垂直同步、
顶满 **75 FPS**。

#### 一、两个数字先钉死

- **像素时钟 = 85.7118 MHz。** `sdc/ti60_top.sdc:311` 写的是
  `create_clock -period 11.667 hdmi_tx_slow_clk`，1 / 11.667 ns = 85.7118 MHz。
  反推也吻合：1792 x 798 对它正好是 **59.94 Hz**，与上板读数一致。
  `rtl/ti60_top.v` 里端口注释的"51.25 MHz"是早期残留，已改正；
  `hdmi_tx_fast_clk` 同理是 428.6 MHz（5 倍）。

- **75 Hz 不需要提高像素时钟，压缩消隐即可。**
  85.7118 MHz / 75 = 1.1428 M 像素一帧。

#### 二、新时序：H_TOTAL 1456 x V_TOTAL 782 = 75.28 Hz

| | 旧 | 新 |
|---|---|---|
| H_ACT / H_FP / H_SYNC / H_BP / **H_TOTAL** | 1366 / 70 / 143 / 213 / **1792** | 1366 / 8 / 56 / 26 / **1456** |
| V_ACT / V_FP / V_SYNC / V_BP / **V_TOTAL** | 768 / 3 / 3 / 24 / **798** | 768 / 2 / 3 / 9 / **782** |
| 刷新率 @85.7118 MHz | 59.94 Hz | **75.28 Hz** |

**为什么是这两个数**（`tmp/calc_timing.py` 把候选全算了一遍）：

- **刷新率要略高于 75，不能正好 75.00。** HUD 的 FPS 是硬件每 1 秒数一次
  scanout 交换次数（`bitblt_apb_regs.v` 的 `second_ticks == CLOCK_HZ - 1`）。
  75.00 Hz 时 75 个帧周期正好 1000.0 ms，相位稍偏就数到 74；
  75.28 Hz 下 75 个周期是 **996.3 ms**，稳定读 75。

- **消隐怎么切，是这一节真正的取舍。** 两条轴都得压（水平从 426 像素压到
  90，垂直从 30 行压到 14 行），但压重的后果不一样：

  - **H_SYNC 0.653 µs**（1366x768@60 标准是 1.67 µs）。短，但仍在常见 HDMI
    接收端能锁住的范围内；
  - **H_BP 0.303 µs**，**H_FP 0.093 µs**；
  - **垂直消隐 14 行 = 237.8 µs**（标准 30 行）。如果把水平留宽、垂直压狠，
    垂直消隐只剩 137 µs —— 所以宁可让 H_SYNC 短一点，也要把垂直消隐留住；
  - **V_SYNC 保持 3 行 = 51 µs**，与标准脉宽一致（显示器认的就是这个边沿）。

  **这仍然是非标准时序。** 现代 LCD 用缩放器处理 1366x768 输入，对消隐不敏感，
  但**这一点只能在板上确认**。

- **扫描侧的余量核对过**：一条有效行 15.94 µs，而 VDMA 一行读 342 个 128-bit
  word、@100 MHz 是 3.42 µs —— **4.6 倍余量**；整帧 DDR 需求 316 MB/s
  （文档既有的 24.6% 占用结论不受影响）。`TOTAL_BURSTS` 跟的是 `V_ACT` 而不是
  `V_TOTAL`，压消隐没有碰它。

改动落在 `rtl/v_dma/video_dma_read.v` 的参数默认值上（`ti60_top.v` 的实例化
只覆盖 `H_ACT` / `V_ACT`，其余走默认值）；**sdc 一个字没改**，因为像素时钟
频率没变。

#### 三、正常游戏：一帧吃两个 vsync -> 一帧一个

**真因**：帧循环里有两个"每显示帧只发生一次"的等待，而它们其实是**同一个事件**。

```c
for (;;) {
    gpu2d_wait_vsync();                              /* 等帧首脉冲 */
    ...
    while (GPU2D_REG_RIGHT_ACTIVE == right_back) { } /* 等扫描出交出 back buffer */
    game_frame(...); publish; flip;
}
```

RTL 里这两件事在**同一拍**发生：`video_dma_read.v` 里
`active_base <= next_frame_base_addr` 和 `vsync_flag = frame_clear_axi` 都来自
`(v_cnt == V_ACT) && (h_cnt < 16)`。所以循环**每帧要等两个脉冲**，
60 / 2 = **30 FPS**。

**改法**：游戏这一场去掉 `gpu2d_wait_vsync()`，**只留双缓冲握手**。

```c
if (screen_state == SCREEN_MENU)         menu_wait_vsync();
else if (screen_state == SCREEN_GAME)    { /* 只留握手 */ }
else if (screen_state == SCREEN_BITBLT)  { /* 同上，见第四节 */ }
else                                     gpu2d_wait_vsync();   /* stress */
```

**为什么留握手、去脉冲**：握手（`RIGHT_ACTIVE == right_back`）挡的是"写正在被
扫描的那块 buffer"，那是**撕裂**，不是"慢"，所以必须有；而在有握手的前提下，
帧首脉冲是**多余的第二个闹钟**。垂直同步本身**仍然有效** —— 画面不撕裂，
只是不再被等两遍。

#### 四、双屏对比：关掉垂直同步

CPU vs FPGA 那一场**彻底不等帧首脉冲**：循环顶部的 `gpu2d_wait_vsync()` 跳过，
保留 `while (RIGHT_ACTIVE == right_back)` 和 `while (LEFT_ACTIVE == left_back)`。

**取舍**：这一场要的是"两种渲染方式真实的天花板"，所以**人为的帧率限制全部
去掉**。但**没有**连双缓冲握手也摘掉 —— 那样等于往正在被扫描的 buffer 里写，
出来的是撕裂画面，两个数字就不可比了，而且工作台的 ownership 断言会直接拒绝
（`BitBlt wrote the SCAN active right buffer`）。去掉脉冲之后，FPGA 半边的上限
就是**扫描出每帧放行一次**，也就是屏幕的刷新率（75.28 Hz）——
**这条"上限"过去只是读数备注，现在被本节新增的「六」提为验收线。**

#### 五、读数（如实记录）

| | 实测（指令数/帧） | 换算到 100 MHz 的板子 | 上板应有的读数 |
|---|---|---|---|
| **FPGA 半边**（BitBlt） | **818 181** | 8.18 ms -> 122 FPS | **75**（被 75.28 Hz 垂直同步封顶） |
| **CPU 半边**（软件逐像素） | **9 000 000** | 90.0 ms -> 11.1 FPS | **11** |
| 差 | **11.0 倍** | | **6.8 倍** |

**必须说清楚的一点**：这两个是**指令数**，不是板上读数。工作台把"一个显示帧"
建模成**固定的 25000 条指令**，而板子上是 13.3 ms（约 133 万条），两者比例
完全不对 —— 所以工作台里跑出来的"每显示帧多少帧"没有意义，有意义的是**每种
渲染要花多少条指令**，那个可以一比一换算（板子是 100 MHz 单发射）。**真正的
读数在上板后的 HUD 上：左侧是 CPU、右侧是 FPGA。**

CPU 半边那 900 万条指令几乎全是 `cpu_fill()` 的逐像素写（一轮 10 片里有 2 片是
640x384 的清屏，各 245 760 像素），所以那个数字是**纯计算**，换算出来就是板上
的 90 ms，没有仿真水分。FPGA 半边那 818 181 条里含 BitBlt 引擎的等待自旋
（工作台把引擎建模成"忙到某个 step"），**板上只会更快**，所以 122 FPS 是
保守值。

**怎么验证的**：

1. **帧循环里的 vsync 轮询次数** —— `tmp/diag_vsync_trace.py` 挂 `vm.load`
   记录读 APB 0x24 / 0x2C 的时间戳：

   | 12 个显示帧的窗口 | 读 0x24（VSYNC_STS） | 读 0x2C（RIGHT_ACTIVE） |
   |---|---|---|
   | 改之后 | **0 次** | 6 个轮询循环，间隔 50000 步 |

   0 次就是"游戏这一场已经完全不看帧首脉冲了"，只剩握手。

2. **把工作台的显示帧加宽，看帧率跟不跟得上** —— `tmp/diag_fps_wide.py`。
   工作台里游戏一帧约 35 000 条指令，而它把显示帧定死成 25 000，所以模型里
   循环是**渲染受限**的，读数必然是 0.50。把模型帧放宽：

   | 模型显示帧（指令） | 读数 |
   |---|---|
   | 25 000（工作台默认） | 0.50 帧 / vsync |
   | 50 000 | **1.00 帧 / vsync** |
   | 200 000 | **1.00 帧 / vsync** |

   也就是说：**只要渲染装得进一个显示帧，循环就是一个 vsync 一帧**。板子上一个
   显示帧是 133 万条指令，而游戏一帧是 3.5 万条 —— 差 38 倍，所以板上就是
   75 FPS。

3. **双屏的读数**：`tmp/diag_bench.py`，进 RENDER LAB 后跑 900 万条指令，
   数 `GPU2D_REG_RIGHT_NEXT` / `LEFT_NEXT` 的变化次数，再除以总指令数。

#### 六、对比模式（RENDER LAB）的 FPGA 侧必须回到 75 FPS

**为什么单列一条**：本节前面把双屏对比定成「关掉垂直同步、不限速、如实记录、
**不设合格线**」，读数表里 FPGA 侧写的是「被 75.28 Hz 垂直同步封顶到 75」。
那句话只**描述**了当时的状态，没有**规定**它必须一直是 75 —— 后面无论是中期美术、
Phase 1 的硬件光效，还是压测负载，只要把对比侧压下去，文档里没有任何一条会拦住它。
所以这里补上验收线。

**口径先说清楚（这是硬约束，不是期望）**：
对比模式**保留双缓冲握手**（`while (GPU2D_REG_RIGHT_ACTIVE == right_back)`），
握手只在扫描出交换 buffer 的那一刻放行，所以它的天花板**就是屏幕刷新率 75.28 Hz**。
由此推出两件事：

- FPGA 侧的合格表现**只有一种**：读数稳定在 **75**；
- 一旦渲染装不进一个显示帧，读数**直接腰斩到 37/38**，中间没有过渡值。

**验收标准（新增，上板实测）**：

- [ ] 进入 RENDER LAB，连续观察 ≥10 秒：右侧 **FPGA 侧读数稳定 = 75**，全程不得出现 37/38 的腰斩；
- [ ] 左侧 **CPU 侧读数如实记录**（软件逐像素渲染，本来就慢，不设合格线，只作为对照）；

**红线：引擎不是对比模式的私有硬件（牵一发动全身）**

BitBlt 引擎**同时是正常游戏每一帧的渲染引擎** —— 弹幕、精灵、HUD 侧栏、damage 恢复
全部走它。对比模式只是它的另一个调用方。所以修这一条时必须守住：

1. **优先在对比模式自己的帧循环里解决**。这些是 `main.c` 里 SCREEN_BITBLT 分支的局部
   参数，改了不影响游戏逻辑：等待策略（要不要 `gpu2d_wait_vsync()`）、
   CPU 半边的切片调度（`subframe_slice` 与 10 片的分法）、场景规模
   （`NUM_ENTITIES` / `sprites_build` 的物体数）、面板重绘条件
   （`stress_panel` 式的"只在 BCD 变化时重画"）、以及渲染顺序。
2. **不得为了对比侧的读数去动引擎的参数或数据通路**：
   `MAX_BURST_BEATS` / `READ_FIFO_DEPTH` / `DST_FIFO_DEPTH` / `RD_MAX_OUT` /
   `PREFETCH_BEATS` / burst 长度策略 / `Axi_Mux` 的仲裁优先级与通道掩码。
   这些一改，正常游戏的每一帧都跟着变 —— 而且历史上正是这里出过事故：
   `rtl/bitblt_top.v` 顶部那段注释记着，让多个 burst 同时在飞"在理想化测试台上通过、
   却把板子挂死"，最后退回到一次一个 burst、改用加长 burst 的方案。
   真要做，必须**单独立卡、单独上板、单独回归**，不能夹在对比模式这条里顺手改。

   > **例外（避免与本套任务卡自相矛盾）**：《02_分步实施任务卡.md》的**任务卡 13**
   > 本身就把「优化 AXI 突发仲裁与 DDR 队列优先级」列为授权范围。那是**以整机极限
   > 负载为目标、单独上板、单独回归**的独立任务，不属于本条禁止的对象。
   > 本条禁止的只有一件事：**夹带** —— 借"让对比模式读数好看"的名义，顺手改掉
   > 正常游戏也依赖的引擎参数。
3. 任何涉及 RTL 的改动（包括"只是调个参数"）都必须同时满足：
   - `build_hw.bat` 全 PASS、时序 **0 违规**；
   - 24 个仿真场景全过（尤其 `render` 分组里判 BitBlt 命令数与 OP_COPY 逐字节一致的两条）；
   - **回到正常游戏复测 75 FPS 基准**（第一节的验收线），确认没有把游戏拖下去。

**月尘斜向飘的实现提示**（本节需要新做机制的地方）：

现在 `stage_strip_render()` 只有竖直滚动（每帧源偏移 +1 行）。斜向需要
**源偏移同时改变 x 和 y**：

```
src = MM_STRIP_LAYER + (scroll_y * MM_STRIP_LAYER_STRIDE) + scroll_x * 4
```

但现在的视差层只有 1088 宽 × 568 高、只够 y 方向滚，x 方向一滚就出界。
所以要么把层加宽成"宽度 + 斜向总行程"，要么改成一个更大的点阵层
（比如 512×512 的月尘 tile 按相位偏移 blit）。**这一块需要重新算预算**，
建议先在纸上把行程算清楚再动代码。

> **为什么它留在中期**：视差层加宽会**改变 DDR 占用，并影响压测时"全开视差"的负载**，
> 所以它属于「压测用得上的东西」；而月亮、云、星、倒影这些只是好看，去后期。

## 三、压力测试

> **本节范围**：不只是"建个压测关卡"，还要**把《未调用资源使用指南.md》
> 的压榨方案（P0~P3 梯队）一起用上** —— 既压帧率，也压资源余量。

**目标**：用上全部能力，极限堆载，验证系统在满负荷下仍能保持 **75 FPS**，
并且**资源（BRAM / DSP / SRL8 / XLR）仍在安全范围内**。

### 3.1 模式入口

1. **单独建立一个模式入口** —— 与正常游戏流程分开，可独立进入
   （例如主菜单新增一项，或一个独立的启动路径）
2. **进去直接就是 BOSS** —— 跳过开场、道中、关卡进度提示等前置流程
3. 退出后能回到原流程，不影响正常模式

### 3.2 负载要求

1. **BOSS 连续释放各种招式与特效** —— 把第二节做出来的东西全部用上
2. **疯狂堆弹幕** —— 把子弹池堆到上限，制造最坏情况
   （当前池大小：敌弹 192、玩家子弹 128、敌人 32、物品 16）
3. 特效、粒子、视差、全屏效果**全部开启**
4. 负载要能**持续**，不是闪一下就结束

### 3.3 用上《未调用资源使用指南.md》

另一份指南的 §五 给了四档压榨方案，压测要把它们**当作负载的一部分**用起来：

| 梯队 | 定位 | 压测里怎么用 |
|---|---|---|
| **P0** | 零资源成本，先做 | 直接开启，作为压测的基础负载 |
| **P1** | 小资源、直接看得见的观感收益 | 开启，观察它对帧率的影响 |
| **P2** | 吃 SRL8，为高级后处理铺路 | 开启，验证 SRL8（当前仅 4.9%）能否扛住 |
| **P3** | 大改动，为架构升级铺路 | 评估是否纳入本轮压测；纳入则单独记录数据 |

同时按该指南的三条硬结论自查：

1. **BRAM 是唯一紧的资源**（151 / 256 = 58.98%）；DSP 闲 80%、SRL8 闲 95%、XLR 闲 52.8%
2. **SRL / DSP 救不了 BRAM** —— SRL8 总容量只有 BRAM 的 5.6%，DSP 根本不能存数据
3. **新功能优先选「不增加 BRAM」的算术型实现**（DSP / XLR / SRL8）

数据来源：`outflow/ti60_top.res.csv`（Efinity 层级资源报告）。

> 该指南 §1.3 与 §7.5 各留了一处「待核实」，压测阶段一并确认。

### 3.4 量化指标

压力测试必须给出**数字**，不能只说"看起来还行"：

| 指标 | 说明 |
|---|---|
| 平均 FPS | 整段测试的平均帧率 |
| 最低 FPS | 最坏一帧的帧率（关键指标） |
| 帧时间分布 | 是否有超过 1 帧时间的尖峰 |
| 屏幕上的弹幕峰值 | 同时在飞的弹幕数量 |
| BitBlt 命令数 / 帧 | 每帧提交多少次搬运 |
| DDR 带宽占用 | 峰值与平均 |
| **BRAM / DSP / SRL8 / XLR 占用** | 开启 P0~P3 后的实测值 |
| 固件余量 | 测试固件是否仍不溢出 |

**数据来源**：HUD 的 FPS 读数 + `telemetry` 块（`MM_TELEMETRY_BASE`）+
`outflow/` 里的资源报告。

### 3.5 验收标准

- [ ] 可以在不经过正常流程的情况下直接进入压力测试
- [ ] 极限负载下**稳定在目标帧率**
- [ ] 无掉帧、无撕裂、无画面错乱
- [ ] 给出 3.4 全部指标的量化数据表
- [ ] BRAM / DSP / SRL8 / XLR 均未越界

## 四、后期美术优化

> **本节范围**：**可有可无的画面优化**。
> 判断标准：**它不服务于压力测试** —— 压测压不到、也不增加可压负载。
> 因此它排在最后：前三项做完，系统已经能跑、能看、能压，这一节纯属锦上添花。
>
> 本节允许**随时裁剪**：任何一项砍掉都不影响前三个阶段的验收。

### 4.1 第 3 关的观感元素

2.2 已经规定第 3 关要有月亮、并且月尘改成斜向飘。这里补的是**好看的层次**：

| 元素 | 要求 |
|---|---|
| **月亮** | 场景里要有一个月亮（位置、大小、是否有月晕，由实现者定） |
| 云 / 星 | 按 `当前素材图/fairytale/` 的构图补足天穹层次 |
| 地平线 / 倒影 | 梦境该有的元素，参考四张绘画层的元素密度 |

> 同样**只借构图和元素**，仍然走程序化绘制（原因见 2.2：
> 那套绘画 RLE 要 18 kB，塞不进固件）。

### 4.2 HUD / UI

| 项 | 说明 |
|---|---|
| **HUD 是否玻璃化** | 当前侧栏是**纯色块 + 硬边**，全工程 alpha 混合只用在自机光晕和激光条上，HUD 一次都没用 |
| **右侧空出来的区域放什么** | 进度条和 BOSS 血条挪走后，右侧会空出约 180×400 |

> HUD 是静态观感，压测压不到它，所以从原「特效补完」的 E 项挪到这里。

### 4.3 第 2 关火山口喷发处的细化

> 严格说这也是观感项 —— 它不产生压测负载，所以放后期。
> 若中期有余力，可提前做；做了也不影响任何验收。

**现象/要求**：第 2 关火山口喷发的位置太粗糙，需要更细致的刻画。

**当前原件的现状**（v6 的 `build_lava()` 注释里写着这段的历史）：
喷发口现在是"一条 19 像素宽的火口 + 30 个余烬点"，而且注释里明确记录了两次失败的
尝试——先是一块平底光板（贴在锥顶上，看着像贴纸），改成椭圆光斑后"在远看时会被读成
太阳"。所以这里**不是没画，是画得不够**。

**要求**：把喷发处做细致。可以考虑的方向（自行取舍）：

- 火口本身分层（外沿暗红 → 内沿亮橙 → 中心炽白）
- 熔岩流从火口往下淌的痕迹（现在的"裂纹"在山脊上，不在锥体上）
- 喷发柱/烟羽往上（与已有的"余烬"衔接）
- 余烬从火口**向外扩散**而不是均匀撒在锥体上

### 4.4 其它可选的画面优化

- 中期做出来的特效在**非压测场景**下的额外打磨（不影响压测负载的部分）
