# 底牌

> 目标：撑住未来的"更多弹幕 + 弹幕光效（alpha/发光）"，而不是只修
> 当前的 BOSS 掉帧。四张牌按"每行成本 -> 行数单价 -> 光效成本 ->
> 逻辑时间"的顺序组织，每一张都对应未来压力的一层。
>
> 审查依据：代码（memory_map.h / main.c / bitblt RTL）+ tb 仿真 +
> 测试1~4 板级实测。数字全部是实测账。

---

## 牌 1：弹幕行数压缩（多弹幕的"单价"杠杆）

**压力模型**：引擎成本 = 行数 x 每行延迟。弹幕数量翻倍，行数翻倍。
所以"每发子弹占几行"就是弹幕容量的单价。

**审查（memory_map.h 实测）**：
- 敌弹瓦片 9x9 = 9 行/发；满池 192 发 = 1728 行。
- 玩家子弹瓦片 7x26 = 26 行/发（7x7 弹头 + 19 行拖尾）；满级 90 发
  = 2340 行。玩家子弹才是行数大头。

**改法与收益账**（BOSS 帧 r=11727 行、每行 ~119 cyc 实测）：
- 敌弹 9 -> 7 行：单价 -22%，满池省 384 行（约 0.46ms）。
- 玩家拖尾 26 -> 16 行：单价 -38%，满级省 900 行（约 1.1ms）。
- 合计省 ~1284 行 ≈ 1.5ms/帧；等效"同样预算弹幕容量 +50%"。

**审查新增的两条注意**：
1. 敌弹 9 -> 7 若不同步缩小碰撞判定矩形，会出现"看着没中却中弹"
   的判罚——视觉尺寸和判定必须联动，这是玩法改动不是纯视觉。
2. 玩家拖尾是纯视觉（判定只在 7x7 弹头），缩短无玩法影响，只改
   曳光观感。

**验证**：VM 场景 bulletpool / spawn / clamp（判定联动后必跑）+
上板 r 字段。

## 牌 2：光效成本控制（多光效的控制阀）

**审查（tb 实测，LAT=150）**：
```
9x9   COPY 182.0 cyc/row   ALPHA 347.0 cyc/row   比值 1.91x
64x64 COPY 199.6 cyc/row   ALPHA 388.6 cyc/row   比值 1.95x
```
真 alpha 每行 = COPY 的 **1.9 倍**（rd_done 翻倍：源读 + 背景读两路）。
原因：OP_ALPHA 每行读两路（源 + 背景）+ 逐像素混合 + 写，且两路读
共享同一个读 master，读队列被分薄。

**预烘焙的账**（同一张光效的两种做法，用 9x9 行成本算）：
- 真 alpha 光弹 7 行 ALPHA = 7 x 1.9 = 13.3 行等效；
- 预烘焙光晕瓦片 11x11 COPY = 11 行等效——**光晕边 <=5px 时预烘焙
  反而更便宜**；光晕更大（15x15 = 15 行等效）时 alpha 才反超。

**结论与边界**：
- 预烘焙（colorkey）只有 1 位透明，做不出柔光渐变，只能做"多圈
  递减色环"的硬边像素光晕——这是像素弹幕游戏的主流光效，但风格
  要你验收；
- 柔光/大光晕 -> 真 alpha，且只给 BOSS 弹、大弹（牌 2 与分级捆绑）；
- 当前全游戏仅 3 处真 alpha（月亮辉光、激光 glow、玩家 aura），
  弹幕零 alpha——未来加光效时默认预烘焙，别开运行时混合的口子。

**验证**：gen_alpha_vectors.py / alpha 场景 + 上板 g 字段对比。

## 牌 3：规律层硬件合成（多光效的"免费层"）

**审查（已上板的天气模块为证）**：凡是"全屏统一或有规律"的层，都
可以像天气（雪花）那样在 scanout 端用几个寄存器合成，引擎零负担、
资源可忽略（170 点表 + 8 比较器只占 Ti60F225 的几百分之一）。

**适用清单（未来光效的大头）**：
- 激光柱（多列场景）
- 符卡背景脉冲、全屏亮度调制、色偏滤镜——逐像素变换，scanout
  端组合逻辑即可；
- 屏幕泛光：需要几行 line buffer 做小邻域，中等复杂度，可行。

**边界**：
- 弹幕本体（位置随机、有碰撞、每帧变）不能合成，只能走引擎；
- 大核卷积（真 bloom）scanout 端做不了。

**验证**：tb 仿真（tb_weather.v 同款）+ 上板观感验收。

## 牌 4：异步管线化渲染（给弹幕逻辑腾时间）

**审查修正（测试 3/4 实测）**：BOSS 帧 j = 14.3-18.4ms，
g = 11-14ms，j-g = 2-4.3ms（CPU 逻辑 + 命令下发）。异步化把这部分
藏进引擎时间，j 趋近 g。**收益 = 2-4.3ms/帧（15-25%），不是之前
讨论的 30-40%——瓶颈在引擎，CPU 只有这么多可藏。**

**前提与代价**：
- 硬件命令 FIFO（CPU 一口气下发整帧命令，引擎连续执行）是前提，
  没有它 CPU 下发时仍要等引擎空闲，藏不住；
- 固件渲染/逻辑分离 + 双缓冲重构，工程量是前面所有牌之和；
- 输入到画面延迟 +1 帧（13ms）——弹幕游戏对手感敏感，需验收。

**收益边界**：只藏 j-g，引擎 g 本身一分不动。救不了"引擎超预算"，
只能让 j 贴着 g 走。

**验证**：tb_bitblt_suite 加连发命令场景（FIFO 功能）+ 上板看 j 是否
趋近 g。

## 明确不做

- 手搓 DDR 控制器：几周工程量换不确定收益，账算不过来。
- 降分辨率：最后手段，四张牌打完再说。
