# Ti60 2D 图形加速引擎 — 独立脱板仿真工作台

本目录是工程自带的 **RISC-V 软核 + APB3 + BitBlt 加速引擎 + DDR3 显存** 虚拟仿真工作台。
无需开发板即可离线验证固件逻辑、寄存器时序、双缓冲翻盘，并导出 1366×768 渲染图。

从本次收尾起，工作台运行的是 **GCC 编译出来的真实固件**（`sw/build/firmware.bin`），
不再是 Python 现场拼出来的机器码；同时补齐了 **OP_COPY（块拷贝）字节级模型**，
以及 **OP_ALPHA（硬件 Alpha 混合）字节级模型**——含实时背景读回、Color Key 优先级、
背景 alpha 字节透传与全局 alpha 缩放。

## 目录结构

| 文件 | 作用 |
| :--- | :--- |
| `run_sim.bat` | 一键：先用 GCC 构建固件，再跑全部仿真并导出图片 |
| `rv32i_soc_vm.py` | 虚拟机核心：完整 RV32I 解释器、APB 外设、**BitBlt FILL/COPY/ALPHA 字节级模型**、DDR/显存、分屏所有权护栏 |
| `test_runner.py` | 24 场景自动化验收，含 OP_COPY 与 OP_ALPHA 完整性比对 |
| `blit_ref.py` | BitBlt 引擎的架构参考模型（与 RTL 共用向量集做交叉验证） |
| `alpha_ref.py` | OP_ALPHA 的独立参考模型（实时背景读回 + 定点混合 + Color Key） |
| `output/` | 导出的渲染图（BMP/PNG） |

## 使用方法

场景按 **id + 分组** 组织，单次运行有十分钟的预算上限；每个场景都从缓存的
"开机快照"恢复，不再重走 7700 万步开机。

```bat
:: 列出现有场景 id 与分组
python simulator\test_runner.py --list

:: 按分组短跑（推荐）
python simulator\test_runner.py --group render     :: 渲染 / 拷贝 / Alpha
python simulator\test_runner.py --group play       :: 弹幕关操作与菜单
python simulator\test_runner.py --group regress    :: 拾取 / 满级 / 弹池 / 消抖 / 大招 回归
python simulator\test_runner.py --group settings   :: 暂停 / 设置界面
python simulator\test_runner.py --group explore    :: 关卡推进（小怪→道具→BOSS）
python simulator\test_runner.py --group backdrop   :: 三关背景切换（最重）
python simulator\test_runner.py --group stage1     :: 特效 / HUD / 第三关 BOSS / 开大边界（回归）
python simulator\test_runner.py --group stage2     :: 大招演出 / 四个基础敌方技能
python simulator\test_runner.py --group stage3     :: 五个进阶敌方技能（阶段三）

:: 只跑指定的几条
python simulator\test_runner.py --only alpha,edge

:: 全套（只在需要一次性总账时用，远超单次预算）
python simulator\test_runner.py --suite --export-images

:: 固件改动后重建开机快照（唯一会走完开机的路径）
python simulator\test_runner.py --refresh-snapshot --group regress

:: 指定其它固件镜像（.bin 或 .elf）
python simulator\test_runner.py --source ..\sw\build\firmware.elf --group render
```

### 开机快照

固件开机要预解码三张 1366x768 背景 plate 加一条 32x768 视差条（约 314 万 RLE
像素），在一个没有乘法指令的 RV32I 软核上折合 **8110 万模拟步 / 约 120 秒宿主时间**
（2026-09-22 实测，`tmp/diag_boot.py`）。每个场景都从零开机的话，光开机就把预算
吃光了。

底板像素数从 120 万涨到 314 万而开机只多了 400 万步，是因为上一版"用矩形画"
的底板本身也要为每张板发几十条 FILL 并逐条等引擎 —— 省下的数据是用命令换的。
见 `残留.md` 第 4 条。

因此 `test_runner.py` 第一次运行时把"第一帧菜单已发布"的整机状态
（RAM + DDR + 显存 + 寄存器，约 25 MB）缓存成
`simulator/cache/boot_<固件哈希>.pkl`，之后每个场景从它恢复，开机开销降到约 1 秒。
快照文件名带固件哈希，**换固件后自动失效**；也可以 `--refresh-snapshot` 手动重建。

### 仿真里的「一帧」，以及它为什么不能代表真板

`rv32i_soc_vm.py` 的 `TICK_STEPS = 25000` 是**建模的 60 Hz**：虚拟机每 25000 步
置一次 VSYNC，固件要等到那一步之后才开始下一帧。`test_runner.py` 的 `TICK = 25000`
与它同值，所以**在仿真里「TICK 步 = 一帧」是精确成立的**（实测 25000 步/帧），场景里
用 TICK 写的循环既不会漏帧也不会多跑一帧。

它**不等于真板的一帧**。真板一帧的 CPU 侧工作量取决于渲染耗时，而工作台的 BitBlt
开销模型是「每条命令固定 10 步」，与搬运量无关。由此：

* 仿真能可信地判定**逻辑**：谁在第几帧做了什么、状态机走到了哪一步；
* 仿真**不能**判定真板的帧率，也就不能直接判定「慢动作」。

### 命令数才是这里唯一能映射到真板时间的量

工作台不模拟 BitBlt 引擎的吞吐，但**逐条统计命令**（`vm.blit_fill_calls` /
`vm.blit_copy_calls`）。真板上一条 16×480 的窄条 FILL 要激活 480 个 DDR 行、每行只
写 64 字节，和一次 640×600 的整版 blit 完全不是一回事，所以**每帧命令数**是这里唯一
能拿来判断真板耗时趋势的量。实测（弹幕关，固件 2026-09-21 版）：

命令数只是三个量里的一个。真板为每条命令付出的是**它触及多少 DRAM 行**
（引擎每行一次 AXI burst、一次 DRAM 行激活），以及**每个 burst 搬多少有效字节**，
所以工作台现在同时统计三者（见 `temp/stage2_diag/probe_14_cost.py`）。
实测（2026-09-22 固件）：

| 场景 | 命令/帧 | fills | copies | **DRAM 行/帧** | Mpx/帧 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| 平时 | 104 | 19 | 84 | **4411** | 0.90 |
| BOSS 战（未开大） | 106 | 22 | 86 | 4509 | 0.91 |
| **BOSS 开大** | **224** | **76** | **148** | **7451** | 0.99 |
| BOSS 弹幕铺满、粒子已过期 | 229 | 81 | 148 | 7152 | 0.96 |

改动之前同一次测量是：开大帧 **545 命令 / 380 fills / 23432 DRAM 行**，
而其中 **10792 行来自 19 条 32x568 的视差条拷贝**——比整帧其它所有命令加起来还多。
现在视差层每关预合成一次，每帧只发一条 640 宽的拷贝：命令 21 变 1，
DRAM 行 21584 变 3408，而且每行的 burst 从 128 字节变成 2560 字节。
敌弹、撞击特效和激光柱同样改成开机预合成，每帧一条拷贝。
**真板的开销是「有多少行、每个 burst 搬多少字节」，而不是命令条数；**
**上一轮只砍粒子数（668 降到 325 条 fills）因此没有解决问题。**
**真板帧率仍然需要上板确认。**

固件自身的指令数（`vm.steps`，1 步 = 1 条指令）也一并记录：开大帧
**100335 降到 49281 步/帧**（平时约 25000，那正好是 VSYNC 周期的空转）。
其中 `__mulsi3` 一项就从 33337 步/帧降到接近 0——这颗 Sapphire 是
`MULDIV_EXT = 0`、`BARREL_SHIFTER = 0`（见 `ip/soc/settings.json`），
每一个 `*` 都是一次 36 字节的移位加法循环。

修复前：BOSS 开大 **668–692 fills/帧**（10 个粒子 × 约 48 次 fill），玩家开大
**234 fills/帧**（4 个粒子）。这就是上板反馈里「BOSS 开大像慢动作」的来源——
一个粒子每帧要发约 48 条 FILL 命令，十个粒子把每帧命令数顶到平时的 30 倍。

### 分组实测耗时（同机串行）

| 分组 | 场景数 | 宿主耗时 |
| :--- | :--- | ---: |
| `render` | 3 | 3.1 s |
| `play` | 4 | 31.4 s |
| `settings` | 1 | 48.8 s |
| `stage1` | 4 | 71.4 s |
| `backdrop` | 1 | 142.0 s |
| `regress` | 7 | 120.0 s |
| `stage2` | 2 | 179.6 s |
| `stage3` | 1 | 39.2 s |
| `explore` | 1 | 232.7 s |

上表是同机实测（2026-09-21，串行、含导出图片，当时全部 **24 个场景**通过）。阶段二任务 02
加了 `hitsweep`、任务 03 又把它扩成「受击全套反馈」之后重测过一次：**7 个场景 120.0 s，
7/7 通过**（`hitsweep` 一个人占 14.7 s——它要逐帧读完那条 1.5 秒的闪白包络）。换固件后的
**第一次**运行会多花约 80-130 秒重建开机快照。**八个分组全部落在五分钟预算内**，
最重的是 `explore` 232.7 s。八个分组串行跑完合计约 14.2 分钟。

耗时变化的方向和原因：

* `explore` 从阶段二的 232.7 s 降到本轮 **150.0 s**（−35%）。方向上有两个候选解释：一是
  本轮回归是**独占机器**跑的（阶段二那次明确记着「回归任务占着 CPU」），二是阶段三给
  `boss_next_pattern()` 加了「避开最近用过的招式」，BOSS 战少了一些重复的重弹幕。
  **本轮仍然没有做归因测量，这只是记账。**
* `regress` 143.4 -> 139.2 s：HUD 水槽那 66 816 像素的搬运还在，视差层的收益仍在抵它。
* `stage2` 179.6 -> **185.3 s**：`skills` 一个人占 175 s —— 它要让弹幕追踪走完 60 帧的布阵
  和 20 帧的驻留，还要应付 48 次强制换招。它现在是九组里最重的一组，仍在预算内。
* `stage3` 38.7 s：本轮新增的分组，`skills3` 一条场景里跑完 8.1–8.5 五条技能，外加
  「第一关 80 次换招必须打全四个新技能」的收尾。

> `explore` 与 `backdrop` **不要同时跑**：两个都会抢满 CPU，串行跑各自都在预算内。

### 这一轮的解释器改动

分派链按实测频率重排（`temp/stage2_diag/probe_opcode.py`：OP-IMM 39.9%、BRANCH 24.0%、
LOAD 15.7%），平均比较次数 **4.59 降到 2.50**；`self.steps % TICK_STEPS` 那个每条指令一次
的取模改成倒计数，并且 `__setstate__` 用 `TICK_STEPS - (steps % TICK_STEPS)` 重建它，
**缓存快照的 VSYNC 相位与原来完全一致**。

**这一轮没有做前后 A/B 计时**（回归任务占着 CPU），所以不给加速百分比——只报告
「比较次数减了 2.09 次/指令」和「每条指令少一次取模」这两个可以直接核对的量。

## 工作台对固件符号的依赖（显式契约）

有些场景没法靠「玩」到达（第三关 BOSS 要跑几分钟），所以工作台会**直接写固件的变量**。
这些变量由 `sw/build_firmware.py` 的 `HARNESS_SYMBOLS` 导出到 `sw/build/firmware.sym`，
**少一个就构建失败**：

> 这曾经是隐式契约——上一阶段直接往 `.bss` 写 `stage_bg_active`，靠的是「符号恰好还在
> 那份导出里」。一旦固件改了布局，场景会以「符号缺失」报错，或者更糟：悄悄写到搬走了的
> 旧地址上，然后以「背景不对」的形式失败。现在构建期就拦住。

当前契约（29 个）：`stage_bg_active` `player_x` `player_y` `wave` `lives` `weapon`
`weapon_level` `score` `atk` `fire_cd` `boss_state` `boss_hp` `boss_hp_max` `boss_x`
`boss_y` `bomb_charge` `invuln` `kills` `hw_accel`
`boss_pattern` `boss_pat_timer` `boss_fire_timer` `cut_phase` `boss_laser`
`menu_sel` `game_particles` `hit_ring_timer` `hit_ring_x` `hit_ring_y`。

后四个是阶段二加的：`skills` 场景要强制某个招式并读回激光切割的相位。
`boss_laser` 让「BOSS 宣告了自己」的场景能先清掉入场那 90 帧激光再给下一张卡打分；
`menu_sel` 是七行菜单当前的行号。`game_particles` 是阶段二任务 02 加的：
受击扫场在每颗被清掉的弹原地留下一个 `PARTICLE_MOTE`，**没有它，`hitsweep`
只能证明子弹没了，证明不了它们是被扫掉的**——池子里的记录也可能只是自己过期了。
`hit_ring_*` 是任务 03 加的：冲击波环锚在**中弹点**，而自机在**同一帧**已经被
甩回出生点，所以「环画在正确的地方」这件事只能靠读回锚点来判，不能靠「环在自机旁边」。

## 与 RTL 的交叉验证（L2）

工作台里的 `blit_ref.py` / `alpha_ref.py` 和 RTL 测试台 `tests/tb_step3_bitblt_copy.sv`
吃同一份向量文件（`tests/bitblt_copy_vectors.txt` / `tests/bitblt_alpha_vectors.txt`），
各自输出逐向量 FNV-1a 哈希，由 `tools/compare_blit_vectors.py` 比对：

```bat
python tools\gen_copy_vectors.py                 :: 生成向量（带边界自检）
python tools\gen_alpha_vectors.py                :: 生成 Alpha 向量（带边界自检）
python simulator\blit_ref.py  --out work_sim\step3_rtl\bitblt_copy_py.vec  --quiet
python simulator\alpha_ref.py --out work_sim\step3_rtl\bitblt_alpha_py.vec --quiet
powershell -File tests\run_bitblt_copy_rtl.ps1   :: 真实 RTL 跑同一组向量（64/16 两种突发）
python tools\compare_blit_vectors.py             :: 拷贝：153/153 必须一致
python tools\compare_blit_vectors.py --tag AVEC  :: Alpha：86/86 必须一致
```
