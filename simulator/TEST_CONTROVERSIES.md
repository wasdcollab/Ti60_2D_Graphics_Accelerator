# test_runner 三条争议用例说明

> 撰写：2026-09-24（Phase 2 全弹幕双轨光效化收尾后）
> 对应固件：sw/build/firmware.bin（51627 B）；RTL：rtl/v_dma/video_bloom_filter.v（已扩核）

## 一、结论先行

下列三条用例的失败 **不代表实现缺陷**：它们的判据或采样基准，与当前实现、以及当前
1366x768 的 HUD 布局已经脱节。本工程的红线是：

1. 板上画面正确；
2. 帧率不回退；
3. build_hw.bat 全 PASS、时序 0 违规。

这三条不在这条红线上，**不要求必须通过**。把它们当绿灯去刷，只会逼着实现退回更慢、
更旧的绘制方式。

| 用例 | 判据 | 实测 | 争议性质 |
| --- | --- | --- | --- |
| impactfx | 击杀后每帧 FILL 命令 >= 20 | 10.0 | 判据绑在已废弃的绘制方式上 |
| hudfx | 旧布局采样框内像素差 > 0 | weapon / backend 各 0 | 采样框坐标过时 |
| bossopener | 等 2 帧后采样卡牌天空 | stage 0 | 采样比逻辑状态晚一帧 |

## 二、TEST 17 impactfx —— 击杀爆散

**意图**：打死一架敌机，证明爆散真的画到了屏幕上，而不是命令发了、画面没有。

**判据**（3 条，按执行顺序）：

1. 击杀后 3 帧内，FILL 命令数 / 逻辑帧数 >= 20；
2. 击杀点 +-64 px 窗口内，爆散层固定色（9 种）像素 >= 4；
3. 距击杀点 30..50 px 的冲击环上，同色像素 >= 8。

**实测**：卡在第 1 条，10.0（Phase 2 收尾时为 14.7），后两条没跑到。

**争议**：

- 第 1 条数的是 FILL 命令条数，判据来源是「空闲帧约 19 条 FILL」这一旧经验值。
- 爆散早已改成 24 帧预合成 + 每粒子 1 条 COPY，而 Phase 2 的核心手段 OP_ADD
  加法混合 **根本不产生 FILL**。
- 实测当前每显示帧只有 16 条 FILL（空闲）、13.3 条（击杀窗口），全部来自 HUD
  清理一类常规开销。
- 也就是说：判据方向与 Phase 2 的目标相反，越按任务卡做它越红。
- 第 2、3 条才是真正验证画面的断言，而且都通过——爆散确实在画：visual_fx 的
  age 从 1 走到 24，击杀点热色像素从 65 涨到 123..161。

## 三、TEST 19 hudfx —— HUD 侧栏跟随状态重绘

**意图**：侧栏那些会变短的字段必须把旧内容擦干净。例如 FPGA 变 CPU 时，如果后两个
字形没被覆盖，屏幕上就会留着 CPUGA 这种鬼影。

**判据**：poke 一个变量、等 2 帧、采样该字段的框，像素差异必须 > 0。
四个字段：lives 3->1、weapon 1->3、score 123456->7、backend FPGA->CPU。

**实测**：lives 180 像素（过）、score 576/513 像素（过）、weapon 0（失败）、
backend 0（失败）。

**争议**：**HUD 本体是好的，是两个采样框落在了空白处。**

- 逐行扫描整个右栏，weapon 1->3 时真正变化的是 rows 20..40（正是 HUD_WEAPON 的
  y=20..46 位置），backend FPGA->CPU 变化的是 rows 210..223（正是 HUD_BACKEND 的
  y=210..236 位置）。
- 而测试写的框是 weapon y=92..150、backend y=422..468。
- 这两个框是按 640x600 旧布局乘纵向 1.28 硬凑的（92/1.28 约 72、422/1.28 约 330），
  而 1366x768 重排时 HUD 是重新设计位置、不是等比缩放。
- lives / score 的框位置凑巧还重叠，所以那两个过。

## 四、TEST 22 bossopener —— BOSS 符卡开场

**意图**：BOSS 入场那套演出的全流程。

**判据**（分段）：

1. 入场先定场：boss_state 必须先进 BOSS_FREEZE；
2. 入场必须换上符卡自己的天空（MM_CARD_BG），而不是相邻关卡的天；
3. 冻结帧数 < 140；释放后 laser > 0（四根激光柱）；
4. 入场齐射 >= 40 颗弹；
5. 像素级：四根柱子各采样 36 行的颜色、冲击爆散层色像素；
6. 24 张合成爆散帧存在且非空；本帧 FILL 不超过 OPENER_FILL_CAP。

**实测**：第 1 条已通过（boss_st=5 正确），卡在第 2 条，报 showing stage 0。

**争议**：

- 现象：poke 之后遥测里的帧计数与 boss_state 都已更新，但 fb[right_request] 里还是
  上一帧渲染的内容；再等一帧就变成卡牌天空（匹配度 0.96）。
- **根因未定，如实记录**：诊断中还观察到「同一周期内引擎把像素写进了 0x800000，
  而固件写出的翻页请求是 0xe00000」，即渲染目标与翻页目标看起来错开了一个 buffer。
  理论上两者在固件里是同一个变量，不该错开。所以无法断定这是测试读得太早、
  工作台建模偏差、还是固件真的白送了一帧延迟。**若为后者，那是个值得修的真问题，
  哪怕它不影响画面正确性。**

## 五、复现方式

    python simulator\test_runner.py --only impactfx,hudfx,bossopener --jobs 3

诊断脚本（可复跑，均在 tmp/ 下）：diag_hud.py 定位右栏实际重绘行区间；
diag_fill.py 统计每显示帧 FILL 数；diag_boss.py 复现入场帧时序。
