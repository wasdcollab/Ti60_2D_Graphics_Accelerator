# STRESS STAGE 审阅与优化记录

日期：2026-10-10。基线为本次修改前的工作区，包含项目已有但尚未提交的修改，不等同于 Git HEAD。用户提供的实板基线是 75 FPS、未观察到缺块。本次完成固件构建与模拟器验证，未重新综合、生成新 bitstream 或下载到实板。

## 新增显示与操作

- `SPRITES`：活动敌人、玩家弹、敌弹、道具、存活玩家与存活 BOSS 的合计。复用现有 telemetry 遍历，不额外扫描对象池。它是活动对象数，包含尚未回收的边缘对象，不是逐像素可见或完整成功绘制的数量；不计天气、粒子、光效和激光特效。
- `Y LOAD`：压力风暴的补充目标，按 Y 在 **192 → 256 → 320 → 384 → 448 → 192** 之间循环。长按只切换一次。BOSS 自身弹幕会另外叠加，所以它不是敌弹总数上限。降低档位不会立即删除已有弹幕。
- `DROP`：当前档位内，单帧被行表拒绝的条目数的峰值。一个条目对应一个 Sprite 的一条扫描行，不是一个完整 Sprite；非零即表明出现容量丢弃。切换档位或重新开始清零。

计数每 16 个逻辑 tick 更新一次，新 DROP 峰值立即触发更新。双缓冲各自保留 HUD 脏标记，避免旧数字残留。默认仍为 192，便于保持原有实板基线。

## 本次性能改动

原行表构建先清零旧条目，再写入新条目；密集稳定场景下，同一地址每帧被重复写入。现在直接覆盖新前缀，仅清除该缓冲区的旧尾部 `[new_depth, old_depth)`，并保留每张表独立的历史深度。热循环去除逐条 bitset 维护，垂直裁剪和行范围更新移至每个 Sprite 一次。

使用真实链接固件的 RV32 指令执行器，注入相同对象位置与顺序，对比修改前后结果。两个版本执行完整 `game_render`，表中指令数统计到行表构建后的标记；关闭压力关 HUD，避免把新增界面成本混入核心算法比较。下列是稳定帧，不包括首次填表。

| 场景 | 原行表指令数 | 新行表指令数 | 指令减少 | 原表写入次数 | 新表写入次数 |
|---|---:|---:|---:|---:|---:|
| 192 敌弹 + 96 玩家弹 | 246,352 | 148,165 | 39.9% | 14,976 | 7,488 |
| 320 敌弹 + 128 玩家弹 | 367,582 | 223,525 | 39.2% | 23,296 | 11,648 |

写入次数是 CPU 对行表的 32 位 store 次数，不能直接当作 DDR 总线事务数；指令数也不等于板上时钟周期或 FPS。完整数据和固件 SHA-256 见 [stress_stage_measurements.json](stress_stage_measurements.json)。

这不是所有分布都更快：少量对象分处屏幕顶底时，范围扫描会遍历中间空行。测试中，这种场景之后的空帧从 2,147 增至 10,667 条行表指令。改动优先优化本次目标的密集压力场景，并保留这个稀疏场景回归用例。

## 仍然限制 Sprite 上限的因素

1. **每条扫描线只有 80 个桶条目。** 两个弹幕池各有 512 个槽，并不意味着任意分布的 1,024 个弹幕都能完整显示。集中在同一高度时先触及行容量，FPS 仍可能正常。此次没有扩大 RTL 行容量；扩大前需要核对 DMA 预取、行内像素处理时限、表布局和资源。
2. **固件 RAM 几乎用满。** 最终镜像含 BSS 和对齐占 64,484 / 64,512 字节，保留原有 1,024 字节栈后仅余 28 字节。下一次增加功能前应先腾出代码空间，不能通过压缩栈预算掩盖问题。
3. **压力关使用混合渲染路径。** 弹幕主要走硬件 scanout overlay，其他图层走 BitBlt；高 Sprite 数不是 BitBlt alpha 吞吐量的等价指标。比赛展示应同时保留独立 BitBlt 对比与 Alpha 测试。

## 验证与复现

固件使用 GCC 15.2.0，`-march=rv32im -Oz -flto -Wall -Wextra -Werror` 构建通过；DDR 地址互斥、HUD 布局、RAM 上限与 BRAM 初始化校验通过。

所选 12 项模拟器回归最终全部通过：基础渲染、Color Key、Alpha、生成、操作、边界、主菜单、弹幕池、受击清屏、压力关、设置菜单、退出清除激光。首轮 10/12 通过，剩余两项因纯 Python 核心缺少原生等待方法而报错；补充等价等待实现后单独重跑，2/2 通过。没有把未执行的其他用例计入通过数。

新增 `tools/test_bucket_rebuild.py`：

- 23 组真实链接渲染器调用，逐字节核对两张完整行表、深度账本与 DROP，覆盖稳定负载、收缩、空帧、满池、同高溢出和上下边缘裁剪。
- 64 帧交互测试，独立统计对象池并与 telemetry 对比，逐像素核对两个帧缓冲的计数区域，检查 Y 键长按与完整档位循环。
- 该交互轨迹出现过活动对象 622、单帧行丢弃 369。这证明溢出可被检测，**不能作为“622 个完整 Sprite 稳定 75 FPS”的证据**。

## 上板步骤

1. 本次已经生成 `sw/build/firmware.bin`、ELF 和 BRAM 初始化文件。现有 `outflow/ti60_top.bit` 仍是旧文件；运行 `build_hw.bat` 重新生成包含新固件的 bitstream，然后按项目既有流程下载。
2. 进入 STRESS STAGE，从 192 档开始，保持开火并观察 BOSS 不同阶段；每档至少观察 10 秒，同时记录 FPS、SPRITES 的范围、DROP。
3. 按 Y 逐档升压。评估完整显示上限时要求 **FPS ≥ 60 且 DROP = 0**，并目视确认画面。DROP 是峰值，短暂溢出也会留下记录。回到低档后需等待旧弹幕消退；要做干净基线比较可退出重进。
4. 达到行容量限制时，下一步应优先评估 RTL 每行容量与集中弹幕分布；若 DROP 始终为零但 FPS 下降，再用板上 profile 计数区分游戏逻辑、行表构建、BitBlt 与等待显示的占比。
