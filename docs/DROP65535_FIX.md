# 1088 负载卡顿及 DROP=65535 修正

用户板上现象：目标 LOAD=1088，活动数约 1082～1087，FPS 降至 10，DROP=65535；
未按 X 攻击也会出现。

## 诊断依据

`bucket_build_finish()` 在分桶协处理器故障或等待超时时，将 DROP 设置为 65535。
因此该数值不是照片中实际丢掉的子弹数。原固件保留故障显示，没有隐藏错误。

恢复版分桶实现每个 32 位条目单独发一个 128 位 AXI 写，只启用 4 个字节。
全局 `video_write_guard` 又限制每笔写必须等 B 响应后才允许下一笔进入 DDR。
数千条描述符因而产生数千次地址/响应等待；先前功能 VM 没有建模此开销。
原硬件测试包含仲裁和反压，但没有把实际写保护器及长写响应等待组合到一起。

写保护器还有独立缺陷：`hold_cnt` 已实现，但其超时放行信号 `hold_out` 没有接入
`admit`，持续视频优先级下可能无限阻止新写请求。已通过旧代码失败、修正代码通过的
定向测试确认。

这两个问题都有仿真证据；是否完整覆盖板上根因，仍需烧录后复测。

## 修正内容

- 每组累计 4 个描述符后写满一个 128 位 beat，保持原来的顺序和表格式。
- 组尾不足 4 个时补零；旧尾部也按 4 项合并清零，覆盖所有旧有效条目。
- 96 个 used 计数合并写入，当前大表由 96 笔减少到 12 笔。
- 保留 AXI 背压稳定性、响应排空、双表及精确计数。
- 接回写保护器的 256 周期有界放行；已经发出的 AW 和已接受的 W 不撤销。
- 硬件 400 万周期看门狗、固件 800 万周期等待保护及 65535 故障显示保持原值。
- 串口末尾诊断字段改为 `B`（APB 0x120 分桶状态，十进制）和 `T`
  （APB 0x12C 当前/最后一次任务周期数），便于板上继续定位。

缓存使用额外两个 BRAM，当前实现资源需以本次构建报告为准。

## 针对性验证

`tools/sim_bucket_board.ps1` 同时实例化真实四路 AXI 仲裁器、写保护器和协处理器。
高优先级读流持续运行，视频写保护优先级每 512 周期有 480 周期有效；
写响应每 1051 周期才提供一次，模拟保守的慢写服务。该延迟是测试条件，
不是从开发板测得的 DDR 时序。

| 1088 负载相同激励 | 结果 |
|---|---|
| 旧 RTL + 旧写保护器 | 4002209 周期、fault=1，实际桶 drops=0；对应固件显示 65535 |
| 合并写入 + 有界写放行 | 1441973 周期、fault=0、drops=0 |
| 第二个缓冲区 1079 项 | 1437766 周期，逐项表内容及 ledger 一致 |
| 两个缓冲区分别清空 | 各 870226 周期，旧描述符全部清除 |

测试开销约降为原故障前等待时间的 36%；这些数值不是板上 FPS。
另通过 6144/8192 池的原分桶回归，包括溢出、奇数长度、移动、候选列表和读响应错误。
有界写服务测试覆盖持续高优先级、AW 停顿、16-beat W、B 停顿和下一笔请求；
旧写保护器回归 15/15 项通过。

## 构建与板上复测

构建命令：`build_hw.bat`；日志：`hardware_drop65535_fix.log`。
本次只生成文件，没有自动烧录。

先复测相同的 LOAD=1088、松开 X 的场景，观察 FPS 与 DROP 是否稳定；
随后保持相同负载再按 X。如果仍出现 65535，可提供串口 115200 8N1 输出中的
`B` 和 `T` 两个字段：B 的 bit31 为 busy、bit28 为 fault，低 16 位为真实桶丢弃数。
保留故障时的值比只看峰值 DROP 更有助于区分 DDR 错误与等待超时。

## 最终构建

map / interface / pnr / pgm 全部通过，100 MHz 核心和 85.714 MHz 像素域时序满足约束。

| 项目 | 数值 |
|---|---|
| XLR | 51155 / 60800 |
| BRAM | 256 / 256 |
| DSP | 66 / 160 |
| core setup / hold slack | +1.365 ns / +0.026 ns |
| pixel setup / hold slack | +1.841 ns / +0.026 ns |
| 固件 bin / 含 BSS 的末地址 | 64252 字节 / 0xF900FCF0 |

固件对首轮发布镜像只有 6 字节差异，反汇编确认均位于 `diag_window()` 的
两个诊断寄存器读取与字段字母，游戏逻辑未修改。小池回归也通过写响应错误注入。

## 后续（2026-10-25）：剩余故障仍在定位

本文的合并写与有界放行只是把阈值从 LOAD 1088 推后到约 1300，没有消除 65535。
串口的 `B`/`T` 两个字段证实任务发生 fault：`B` 的 bit28 是协处理器 fault、低 16 位是真实丢弃数，
一次 1300 发的故障样本是 `B = 0x3000_0000`（drop_count = 0）、`T = 10,027,312`（看门狗 4,000,000）。
旧 `Axi_Mux` 存在地址饥饿缺陷，复现记录见 [BUS_STARVATION_1300.md](BUS_STARVATION_1300.md)。
用户烧录公平仲裁版本后仍出现 fault，因此它不能解释全部板上现象。
本次读取排空修复和 Q 首次错误快照见 [BUS_FAULT_20261025.md](BUS_FAULT_20261025.md)。
