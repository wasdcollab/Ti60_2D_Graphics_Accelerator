# Ti60 弹幕透明方框修复记录

> 2026-10-15 更新：本文以下为双候选历史版本。当前候选已改为全桶非透明覆盖选择，
> 并扩展至 2112 压力档位；实现、验证与待完成实板验收见 [boss_stress_2112.md](boss_stress_2112.md)。

更新：2026-10-10。本记录对应 `outflow/ti60_top.bit`，不要把较早的逐扫描行桶性能报告当作当前八行分组版本的测量。

## 当前交付状态

- 双候选透明回退已实现，并通过 JTAG 下载到 Ti60F225。
- 用户实板反馈：“改善的很好”，当前 HUD 为 **980 sprites / 75 FPS / DROP 16**。
- 这证明当前场景的观感改善和帧率表现；尚不证明 1000+ 元素无丢弃、长期最低帧率不低于 65 FPS。
- DROP 是当前负载档位内**单帧被拒绝桶表项数量的历史峰值**（`bt_drop_peak`），切换档位或重新进入时清零。它不是丢帧数，也不能用 `980 - 16` 得到真实显示 sprite 数。
- **已知边界：只看按 x 范围优先级选出的前两条表项。两条都透明或无效时，不继续找第三条。** 密集三层以上重叠仍可能露出背景。交接要求保留的第三段测试明确检查这一边界，因此不能声称任意深度的暗斑全部消除。

## 实现

1. `rtl/display_engine/2_layer_generators/video_bullet_overlay.v` 使用赢家和第二候选各自的地址、角色号和 hue。赢家非零则选赢家，否则尝试第二候选。
2. 图块配置口仍为 8 位；角色只需 0..31，当前固件实际为 0..28。每份图块 RAM 改为 16384×5，两个独立读库接收相同的启动写入。Efinity 实测每库 10 个 RAM10，两库共 20；原单库 8 位为 16。调色板继续使用块 RAM，没有引入寄存器调色板或不受支持的双读口原语。
3. 修正 RAM 注册输出和 hue/live/DE 的对齐。输入在边沿 N 采样，N+1 图块读取，N+2 调色板读取，N+3 输出 RGB、alpha、visible、add。同步 RAM 的输出本身就是一级寄存器，不再重复注册角色而漏延迟元数据。
4. `simulator/scanout_model.py` 初始化、逐行清除第二候选；空槽以 -1 标记，slot 0 是合法图块。无效行/slot 在两个候选选定后判透明，与 RTL 一致。
5. 敌弹弹体角色 1/2/3 保持 alpha=255；光晕角色 9..26 保持加法哨兵 alpha=254。导弹原有 190/254 混合规则保持不变。

## 下一步：1000+、65 FPS 底线及 DROP

先保留当前已上板版本。当前帧率已达到刷新率附近，下一轮应优先消除桶溢出，而不是用 DROP 掩盖渲染负载。

1. 在同一个 Y 档位保持开火和移动，记录至少 60 秒的活动数、最低 FPS、DROP 峰值，分别测试均匀分布和集中重叠。当前 980/75/16 是用户的一次读数，不是长时间最低值。
2. 在固件桶插入路径记录每组需求峰值、被拒绝表项属于哪种弹体，确认是否主要是八行分组扩大了矩形重叠数量。DROP 的统计口径是表项，不是整个 sprite。
3. 优先比较四行分组与八行分组：前者减少组边界占用，但增加 CPU 建表次数和 DDR 预取量。同步修改固件、DMA 和 Python 的分组常量，并回归 `tb_dma_bucket_group` / 换帧测试。
4. 若确实需要从 128 扩到 160/192 槽，同步检查桶向量宽度、双缓冲表偏移、AXI burst 分段和 **4 KiB 边界**。不能只改 SLOTS：现有预取按两个 burst 处理，非 512 字节步长可能跨 4 KiB。资源也必须重新综合，当前只余 11 个 RAM10。
5. 若三层以上透明遮挡仍明显，需要单独设计更深候选或按真实覆盖筛选的方案。当前三段测试必须保留；修改回退语义时，应将第三段改成对新边界的显式测试，不能删除检查来得到全绿。
6. 完成后以 **1000+ 活动 sprite、最低 FPS ≥65、DROP=0** 和无明显缺块为实板验收目标。背景粒子若另计，应单独列出粒子数，不混入弹幕数来凑 1000。

BitBlt 引擎仍负责背景/图像搬运及其他绘制；本修复处理扫描端弹幕合成，不代表 BitBlt 吞吐率提升。
