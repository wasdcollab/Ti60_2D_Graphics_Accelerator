## 已证实并修正的恢复路径缺陷

`bitblt_axi_read_master.rd_busy` 原来是 `q_full || ar_pend`，只有队列满或 AR 待发才为 1。
队列深度为 4 时，若还有 1～3 笔已经发出的读事务，它会错误地变成 0。
`bitblt_top` 用该信号在 engine_abort 时等待读响应排空，这会让异常后的新命令过早进入，
旧响应可能混入新命令的 FIFO。

现在 `rd_busy` 在任何未完成读取存在时保持为 1，直到最后响应被接受。
没有重置在途 AXI 事务，没有强制取消已经发出的 VALID，没有调整看门狗门限。

`tests/tb_read_drain_busy.sv` 的旧实现直接失败于“仍有一笔未完成读取但报告空闲”；
修正实现通过 1、2、3 笔未完成读取、FIFO 背压、源/目的流标签和最终排空检查。
这证明了恢复路径的缺陷和修正，但还没有证明它是板上第一次 fault 的触发原因。

## 修正验证脚本的误判

`BUCKET_TEST_BUS_LOADED` 原来在全测试累计 tick 超过 500 万时退出，
却把这当作单个任务超过 500 万。几帧通过后，正常的清尾任务也可能因此被中止。
旧日志中 `cycles=497512, fault=0` 的清尾现场不是死锁证据。

现在额外的作业等待检查使用 `busy && cycles > 5000000`，总体测试仍保留独立上限；
补回两个缓冲区的空池清尾验证，脚本在非预期失败时返回错误。

## 新版 Q 快照

串口仍为 115200、8N1；新行包含 `Q... B... T...`。
Q 对应 APB 0x138，替代原串口 z 字段，固件尺寸保持不变。
硬件记录第一次错误，并一直保留到清理 ledger/重新进入关卡或复位。
因此后面即使某一任务恢复正常，仍能读到第一次错误原因。

| Q 位 | 含义 |
|---|---|
| 31:29 | 原因：0 未记录、1 看门狗、2 RRESP、3 RLAST 不符、4 BRESP |
| 28:24 | 协处理器错误现场状态；4 等待读响应，18 清尾，20 排空，26 等待打包写入 |
| 23:20 | 协处理器已接受地址但尚未收到响应的写入数量 |
| 19:10 | 依次为 ARVALID/ARREADY/RVALID/RREADY/AWVALID/AWREADY/WVALID/WREADY/BVALID/BREADY |
| 9:8 | 互联 R 路由选择：0 视频、1 CPU、2 BitBlt、3 分桶；空闲时可能保留上次选择 |
| 7:5 | BitBlt 未完成读取数量 |
| 4 | BitBlt RREADY |
| 3 | DDR 侧 RREADY |
| 2 | 写保护器仍有事务等待 B 响应 |
| 1 | 视频读优先级 |
| 0 | DDR 侧 RVALID |

高 22 位在第一次错误周期捕获；低 10 位总线上下文在下一核心时钟捕获。
状态与计数是现场证据，不把它们自动等同于某一个根因。
B 是当前分桶状态，bit28 为 fault；T 是当前/最后一笔作业的周期数。
解释日志可运行 `python tools/decode_bucket_fault.py --line "F... Q... B... T..."`。
